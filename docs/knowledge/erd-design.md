## 엔티티 도출

- 요구사항의 명사라도 행위 주체로만 언급되고 그 대상만의 관리 기능이 없으면
  엔티티로 승격하지 말고 역할 컬럼(`role`)으로 처리한다. 별도 생명주기가
  생기는 시점에 분리한다. [ch3]
- 동사는 "관리할 기록·증빙을 남기는가"로 판정해 남기면 명사형 엔티티로
  만든다(주문하다→주문서). 명사 추출만으로는 사건 엔티티를 놓친다. [ch3]
- 도출 즉시 기본(회원)/중심(주문)/행위(주문항목·이력) 성격을 태깅한다.
  이것이 개발 순서이자 데이터 증가 예측이다 — 행위 엔티티는 폭발적으로
  쌓이므로 조회 패턴별 인덱스를 이 시점에 예측만 해둔다(선제 구현 금지).
  수동 연도 테이블(`order_2024`)은 만들지 않는다. [ch3]
- M:N을 발견하면 "이 관계가 만들어지는 순간에만 의미를 갖는 데이터가
  무엇인가"를 반드시 묻는다 — 실무 M:N은 거의 항상 숨은 속성(수량·당시
  가격·시각)이 있고, 있으면 이름 있는 연관 엔티티로 처음부터 설계한다.
  [ch3·ch8]
- 약한 엔티티(부모 없이 무의미)는 부모 id 컬럼 NOT NULL로 존재 종속을
  표현한다. FK를 안 거는 이 레포에서는 이것이 유일한 스키마 장치다. [ch3]

## 시점 스냅샷 vs 파생 값 — 경계 판정

concepts.md의 "파생 가능한 사실은 저장하지 않는다"에는 방향이 두 개다:

- 현재 값에서 재계산 가능하면 저장 금지 (기존 규칙).
- **과거 시점의 사실(주문 당시 가격·상품명)은 파생 불가능해지므로 반드시
  관계 엔티티에 스냅샷으로 복사한다.** 원본 참조로 대체하면 과거 기록이
  소급 변조된다. 스냅샷 컬럼엔 "주문 당시 값" 주석을 남긴다. [ch3·ch9·ch12]
- 역정규화(파생 컬럼)는 slow query로 병목이 증명되고 읽기≫쓰기일 때만의
  최후 수단. 그 전에 캐시를 먼저 검토한다. [ch11]
- 통계 테이블이 정당한 조건: 원본 GROUP BY가 서비스 트랜잭션에 부하를
  전파할 때 + **멱등 배치로 언제든 재생성 가능한 캐시**일 때만. 서비스
  로직이 통계 테이블을 진실로 읽는 순간 규칙 위반이다. [ch18]

## 키 설계

- "절대 안 변할 값"이라는 판단 자체를 의심한다 — 로그인 ID·주민번호도
  정책·법 변화로 바뀌거나 저장 금지가 된다(저자 실전 반례: 법 개정으로 PK
  주민번호가 자식의 자식까지 퍼진 레거시 전면 수정). 업무키는 UNIQUE로만.
  [ch5]
- 대리 키는 추적의 전제일 뿐이다 — 값이 언제 무엇으로 바뀌었는지는
  append-only 이력 테이블이 있어야 안다. [ch5]
- 연결 테이블은 복합 PK 대신 **자체 대리 키 + `UNIQUE(fk1, fk2)`**.
  복합 PK는 자식 생기면 키가 전파되고, JPA `@IdClass`를 강요하며, 관계
  정의가 바뀌면(옵션 추가) PK 구조를 바꿔야 한다. 단 복합 UNIQUE를
  빠뜨리면 업무 유일성이 사라지므로 반드시 함께 건다. [ch5]
- InnoDB PK는 클러스터링 인덱스다 — 단조 증가 키는 append만 하고, 랜덤
  UUID는 페이지 분할·단편화 비용을 문다. `UuidBaseEntity`는 외부 노출
  기준으로 고르되 대량 쓰기 테이블이면 이 비용도 계산에 넣는다. [ch5]
- PK는 전 테이블 BIGINT 통일 — INT와의 차이는 1억 건에 ~400MB뿐이고
  INT→BIGINT 마이그레이션은 중단급 재앙이다. [ch11]
- 관계는 비식별(부모 PK를 자식 PK에 포함하지 않음)이 기본. 레포 관행이지만
  명문화돼 있지 않다 — 컨벤션 반영 후보. [ch9]

## 관계 설계

- 1:1의 기본값은 분리가 아니라 **한 테이블 합치기**. 분리 명분 4가지:
  ①크고 드물게 읽는 컬럼 ②민감정보 권한 격리 ③일부만 갖는 0-or-1 부가정보
  ④생명주기·변경 빈도가 다름(주문 vs 배송 — 합치면 NULL 오염·락 경합).
  [ch8·ch12]
- 1:1 분리 시 FK는 **보조 테이블에 + UNIQUE**가 표준(주 테이블 무변경 확장,
  UNIQUE 제거만으로 1:N 전환). UNIQUE를 빠뜨리면 1:1이 소리 없이 1:N으로
  퇴화한다. "살아있는 행끼리만 1:1"이면 storage.md의 `_active_check` 패턴
  (`UNIQUE(fk_id, _active_check)`)을 쓴다. [ch8]
- 참여도 강제의 3층 분담: 설계 문서(ERD)에는 비즈니스 규칙 원형 전부,
  DDL은 강제 가능한 부분만, 나머지는 앱 코드. FK 없는 이 레포에서
  `xxx_id NOT NULL`은 참여도의 절반(값 존재)만 강제하고 참조 유효성은 저장
  전 검증이 메꾼다. "1쪽 최소 참여"(팀엔 최소 1명)는 DB로 원래 불가 —
  부모+첫 자식을 한 트랜잭션으로 커밋하는 조합 Implement의 소관이다. [ch6]
- 조인 뻥튀기: 1→N 방향 조인은 기준 행이 N배 복제된다 — 그 위의
  COUNT/SUM은 조용히 틀린다. 목록+집계 쿼리 리뷰 체크포인트. [ch6]
- MySQL: FK가 참조하는 UNIQUE 인덱스 변경은 FK 삭제→인덱스 삭제→FK 재추가
  순서 필수. 크롤러 소유 테이블(FK 유지) 마이그레이션에 적용된다. [ch8]

## 물리 설계

- **FK를 안 걸면 참조 id 컬럼 인덱스도 없다** — MySQL은 FK 생성 시에만
  자동 인덱스를 만든다. `member_id`류 조회 컬럼은 schema.sql에 인덱스를
  직접 추가해야 풀 스캔을 피한다. FK 금지 규칙의 숨은 비용. [ch12]
- 복합 인덱스 순서: 등호(=) 조건 앞, 범위(<,>,BETWEEN) 뒤. 왼쪽 접두어
  규칙, ORDER BY도 인덱스 순서를 따른다. [ch12]
- 인덱스 추가 판단: 선행 필터가 수백 건 이하로 줄이면 추가 복합 인덱스는
  과잉이다. 주체당 수천 건 + 핵심 병목일 때만, 최종 판단은 EXPLAIN·측정.
  status 든 인덱스는 상태 전이 UPDATE마다 재정렬 비용을 문다. [ch12]
- VARCHAR 길이는 메모리 문제다 — MySQL은 정렬·GROUP BY 버퍼를 **선언된
  최대 길이** 기준으로 할당한다. "넉넉하게"가 디스크 임시 테이블 전락으로
  이어진다. 합리적 최대치(이름 ~50, 이메일 ~100 수준)로. [ch11]
- 금액은 DECIMAL(FLOAT/DOUBLE 금지), 비즈니스 시각은 DATETIME(TIMESTAMP는
  타임존 변환·2038 제약). [ch11]
- **시스템 시간과 비즈니스 시간은 별도 컬럼**: `created_at`은 INSERT 기술
  시각(자동), `ordered_at`류 비즈니스 이벤트 시각은 앱이 명시 주입한다.
  비즈니스 규칙을 created_at으로 판정하면 오판한다. 접미사 구분: 발생
  사건 `_at`, 사용자 지정·예정 시각 `_dt`, 날짜만 `_date`. [ch11·ch12]
- 기간 조건은 `>= 시작 AND < 다음날` 반개구간 — `23:59:59`로 닫으면
  밀리초가 누락된다. LIKE는 전방일치만 인덱스를 탄다(중간 일치는 FULLTEXT
  — `job_posting.content`가 그 사례). [ch12]
- 컬럼명이 너무 길면 축약이 아니라 모델링(분리)을 의심한다. 용어 사전은
  복합어가 아닌 단일어 중심으로 만들어 조합하고, 축약어는 등재·합의분만
  쓴다. [ch3·ch11]
- `created_by/updated_by` 행위자 컬럼은 현재 없다 — 어드민이 데이터를
  수정하기 시작하는 시점에 도입을 검토한다(JPA Auditing으로 자동화 가능).
  [ch12·ch15]

## 공통 코드 · 참조 데이터

- enum vs 코드 테이블 결정 트리: 비즈니스 로직(if 분기)에 쓰이면 enum,
  목록 표시만이면 테이블, 둘 다면 하이브리드. 단 **선제 하이브리드 금지** —
  enum으로 시작하고 운영 변경 요청이 잦아질 때 리팩토링한다. [ch13]
- 하이브리드 운영 규칙: 코드 추가는 개발자가 enum+테이블 동시 반영, 표시
  이름·속성 변경만 운영자 몫. enum↔DB 일치는 동기화 검증 테스트로 강제
  (예: `sigungu.level` ↔ SigunguLevel). [ch13]
- 폐기(deleted_at)와 일시 비노출(use_yn)은 다른 개념이다 — "점검 중 숨김"
  요구가 오면 use_yn(BOOLEAN)을 따로 판다. [ch13]
- 순수 코드 테이블(자연키 code가 정석)과 크롤러 적재 참조 데이터(대리키+
  업무키 유니크 — 재적재 멱등성)는 다른 설계다. catalog에 "코드 테이블이면
  자연키"를 기계 적용하지 않는다. [ch13]
- 코드성 데이터(적고·변경 드물고·조회 빈번)의 표시명 해석은 SQL JOIN이
  아니라 로컬 캐시+TTL(1분 수준)이 1순위 해법이다. sido·sigungu·job_role
  조회가 정확히 이 프로파일. [ch13]

## 계층(트리) 데이터

- 기본기는 인접 리스트(parent_id) + MySQL 8 재귀 CTE. 폐쇄 테이블은 수만
  노드·10단계 이상·초빈번 조회가 실측된 뒤에만. [ch14]
- 재귀 CTE 깊이 제한은 **부모 행 검사**라 N단계까지면 `depth < N`이다 —
  `<=`는 한 단계 더 내려간다. 그리고 재귀 CTE는 JPQL 불가라 네이티브
  `@Query`가 강제된다("파생 쿼리 우선" 컨벤션의 예외임을 알고 시작). [ch14]
- 깊이가 고정된 계층(sido→sigungu 2단)은 계층 모델링 대상이 아니다 —
  레벨별 테이블이 정답. 가변 깊이일 때만 이 절의 도구를 꺼낸다. [ch14]

## 이력 관리

- 도입 판정 4문항: 변경이 비즈니스에 중요한가 / 과거 값 조회가 필요한가 /
  특정 시점 데이터가 필요한가 / 감사 요구가 있는가 — 하나라도 예면 전용
  이력 테이블. 전형: 가격·상태·잔액·계약·권한. 불필요: 로그·임시 데이터·
  거의 안 변하는 마스터. [ch16]
- 기본값은 분리된 **전체 행 스냅샷** 이력 테이블(조회 99%는 현재 데이터).
  컬럼 단위 old/new 로그는 타입 소실·시점 복원 불가로 기본 배제. [ch16]
- **이력은 최초 INSERT 시점부터 기록한다** — 변경부터 기록하면 타임라인이
  끊겨 매 조회가 현재+이력 UNION이 된다. [ch16]
- `valid_from/valid_to`는 시점 조회가 실제 요구일 때만, 마스터성 데이터에만
  — valid_to 갱신은 **append-only를 깬다**(이 레포의 이력 원칙과 충돌).
  없어도 `created_at <= 기준 ORDER BY DESC LIMIT 1`로 단건 시점 조회는
  된다. [ch16]
- 이력 테이블의 시간은 둘이다: 원본 행 탄생 시각과 이력 기록 시각 —
  한 컬럼으로 겸하면 두 질문이 섞인다. [ch16]
- 변경 사유는 `change_type`(표준 코드, 검색용)과 `change_reason`(자유
  텍스트) 분리. 변경 경로가 여럿(앱·배치·크롤러·어드민)이면
  `source_system` 감사 컬럼을 고려한다 — 이 레포는 이미 3주체다. [ch15]
- 공통 audit_log(전 테이블 JSON)는 보조 수단이고 아카이빙 전략이 전제다.
  시스템 로그는 DB에 넣지 않는다(파일+수집 스택) — DB에는 비즈니스 이력만.
  [ch16]

## Soft delete 함정

- **JPQL 조인은 필터의 사각지대다** — Finder 파생 쿼리 밖의 `@Query` 조인·
  통계 쿼리에서 한쪽 테이블의 `deleted_at IS NULL` 누락은 컴파일로 안
  잡힌다. 조인된 모든 soft delete 테이블에 조건이 있는지가 리뷰 체크
  항목이다. [ch17]
- 인덱스에서 deleted_at을 선두 컬럼으로 두지 않는다(대부분 NULL이라 변별력
  없음). 커버링이 필요할 때만 비즈니스 컬럼 뒤에 붙인다. [ch17]
- 생명주기가 복잡한 도메인은 status가 존재 여부를 완전히 대체할 수 있다 —
  `status=CANCELLED`인데 deleted_at도 채우는 이중 관리가 나쁜 설계.
  "별도 라이프사이클이면 베이스 미상속" 규칙의 구체 판정 사례. [ch17]
- soft delete는 개인정보 완전 삭제 요구를 충족하지 못한다 — deleted_at은
  기산점일 뿐이고 "탈퇴 N년 후 hard delete/익명화" 배치 정책을 제품
  결정으로 별도 수립해야 한다. 현재 미수립 — 후속 결정 항목. [ch17]
- 참조되지 않는 테이블(로그·설정)은 "이력 백업 후 hard delete"로 경량 유지
  가능 — soft delete 일괄 적용 관성을 끊는다. [ch17]

## 통계 테이블 · 배치

- 일별 통계 하나면 주간·월간·연간은 재집계로 끝낸다(10년치 3,650행) —
  주기별 테이블을 늘리지 않는다. 실시간 요구는 과거(통계)+오늘(원본)
  UNION ALL — 단 원본 날짜 인덱스가 전제. [ch18]
- **배치는 멱등하게**: 증분 UPDATE(`+=`) 금지. 새벽 일별 배치는
  DELETE & INSERT(한 트랜잭션), 빈번한 마이크로 배치는 UPSERT. 과거
  정정(환불)은 해당 날짜 재실행으로 통일 — 보정 로직을 따로 짜지 않는다.
  [ch18]
- MySQL 8.0.20+에서 UPSERT의 `VALUES()` 함수는 deprecated — 별칭 방식
  (`AS new ... new.col`)을 쓴다. 빈번 갱신에서 DELETE+INSERT는 UPSERT 대비
  2~3배 이상 느리고 갭 락 대기를 유발한다. [ch18]

## 슈퍼-서브타입 · EAV · JSON

- 슈퍼-서브 선택: 유형 적고 고유 속성 적으면 단일 테이블, 유형이 늘고 고유
  속성 많으면 조인 전략. 구현클래스별 테이블(Roll-down)은 UNION·id 중복으로
  배제. 단일 테이블의 실질 비용은 서브타입 고유 컬럼에 NOT NULL을 못 거는
  것. 조인 전략의 키 계약: 자식 PK = 부모 PK(1:1), 외부 테이블은 항상
  부모만 참조. 구분자(dtype) 컬럼은 두 전략 모두 부모에 필수. [ch19]
- EAV는 최후의 수단 — "나중에 바뀔지도 몰라"라는 막연한 걱정으로 도입
  금지. "불확실성이 확실한" 경우(사용자 정의 속성)만, 그때도 핵심 속성은
  컬럼으로 두는 하이브리드가 전제. 레거시가 아니면 JSON이 현대적 대안.
  [ch20]
- JSON 컬럼이 정당한 조건: 카테고리별 상이 속성·예측 불가 스키마·설정/
  메타데이터·스냅샷. 부적합: 자주 검색·정렬·집계하는 값, 참조 필요한 값,
  무결성 핵심 데이터. 검색·집계용 핵심 속성은 일반 컬럼 + 가변 속성만
  JSON. [ch21]
- MySQL 8 JSON 실무: `->`는 JSON 타입 유지(비교용), `->>`는 문자열
  (표시용) — 혼용이 타입 버그의 근원. 경로 검색 인덱스 3종: 가상 컬럼
  (VIRTUAL이 표준)+B-Tree / 함수 기반(8.0.13+, 이중 괄호·타입 필수) /
  배열은 멀티 밸류(8.0.17+, MEMBER OF로만 탐). 부분 수정은
  JSON_SET/INSERT/REPLACE 의미 구분, 배열 관계형 처리는 JSON_TABLE.
  가상 컬럼 도입 시 schema.sql의 H2 공통 문법 제약(STORED/VIRTUAL 키워드
  금지)이 그대로 적용된다. [ch21]
- NoSQL은 프로젝트 95%에 불필요 — RDBMS+JSON 하이브리드로 충분하고, 진짜
  비용은 운영 복잡도다. 확장 한계가 실측될 때 검토. [ch21]

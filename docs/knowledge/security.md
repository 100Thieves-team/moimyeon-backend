# 보안 지식

인증·인가·비밀값에 대해 이 저장소에서 알고 있어야 하는 것. 규칙은 [`../conventions/auth.md`](../conventions/auth.md)에 있고,
여기는 그 규칙만으로는 안 드러나는 함정과 판단 기준이다.

코드를 쓸 때도, 리뷰할 때도 같은 내용을 본다. 쓰는 법은 [README](README.md).

---

## 이 스택에서 걸리는 것

**Kotlin 클래스는 기본 `final`이다.**
Spring이 프록시로 구현하는 보안 애노테이션(`@PreAuthorize` 등)은 `open`이 아닌 메서드에서
조용히 무시될 수 있다. 애노테이션을 붙였는데 안 걸린다면 이걸 먼저 의심한다.
all-open 플러그인이 그 애노테이션을 커버하는지는 `build.gradle.kts`에서 확인한다.

**인증 주체를 받는 방식은 하나로 정해져 있다.**
[`../conventions/auth.md`](../conventions/auth.md)의 "컨트롤러에서 인증 주체 받기" 참고.
컨트롤러에서 토큰을 직접 파싱하거나 자체 검사를 넣으면 그게 오히려 사고 지점이다.
반대로 정해진 방식을 쓰고 있다면 "인가 검사가 없다"고 판단하기 전에 그 경로에
무엇이 적용되는지부터 확인한다.

**인증 기술은 `security-core` 격벽 안에 있다.**
`core`가 인증 라이브러리에 직접 의존하면 아키텍처 위반이자 공격면 확대다.
([`../conventions/modules.md`](../conventions/modules.md))

**로그인은 Google OAuth다.**
`GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, `JWT_SECRET`이 환경변수로 주입된다
(`.github/workflows/ci.yml` 참고). 이 값들이 로그·에러 응답·테스트 픽스처로 흘러가는
경로가 생기면 그건 그 자체로 심각한 문제다.

## 심각도 기준

우리 팀에서 무엇을 어느 급으로 보는지.

| 급 | 해당하는 것 |
| --- | --- |
| blocker | 인증 우회, 다른 사용자 데이터 접근, 비밀값이 로그·응답·저장소에 노출 |
| high | 인가 검사 누락, 외부 입력이 검증 없이 쿼리·경로·명령으로 흘러감 |
| medium | 심층 방어 부재. 지금은 다른 계층이 막지만 그게 사라지면 뚫리는 것 |
| low | 올리지 않는다. 노이즈가 된다 |

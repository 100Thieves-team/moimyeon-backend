> `_workspace/harness-reference/specialist-agents-blueprint.md`)에서 현재
> 스택(core-batch + MySQL, 분석 레이크 없음)에 맞는 부분만 벤더링.
> Glue·Athena·CDC 파이프라인은 분석 요구가 실재할 때 §10에서 다시 가져온다.
>

## 원칙

- **OLTP/OLAP 분리**: 분석·리포팅 목적의 무거운 조회를 운영 DB에 직접
  날리지 않는다. 필요해지면 read replica부터.
- **배치는 재실행 가능해야 한다**: 모든 배치는 "중간에 죽어도 다시 돌리면
  같은 결과"가 기본 계약이다. 멱등성 없는 배치는 리뷰에서 막는다.

## 배치·데이터 이동 변경 시 확인 (pipeline 변경 워크플로우 축약)

1. 스키마 변경이 소비자(다른 배치·API·리포트)와 하위 호환인가.
2. 재실행·중복 실행 시 중복 데이터가 생기지 않는가 (멱등성 키·유니크 제약).
3. 부분 실패 시 상태가 명확한가 — 어디까지 처리됐는지 checkpoint가 있는가.
4. 처리량 변화가 운영 DB 부하 한도 안인가.

## Backfill (과거 데이터 재처리)

1. 대상 기간과 예상 row 수를 먼저 산정한다.
2. 운영 부하 한도를 정하고 rate limit·병렬도를 제한한다.
3. 기존 데이터를 덮어쓰지 말고 별도 출력(테이블·컬럼 버전)에 쓴다.
4. 멱등성 키와 checkpoint로 중단·재개 가능하게 한다.
5. 완료 후 reconciliation: row count·sum·checksum으로 원본과 대조한다.
6. 소비자 전환(cutover) 후에도 기존 결과를 즉시 지우지 않는다.

## 데이터 장애 대응 순서

```text
잘못된 데이터의 전파 중지(배치 중단) → 영향 범위 식별(어느 테이블·기간·소비자)
→ 오염분 격리 → 원본·checkpoint 확인 → 올바른 버전으로 재처리(replay)
→ reconciliation → 소비자 재개 → 기록
```

전파 중지가 항상 1순위다 — 오염 데이터 위에 후속 배치가 돌면 복구 범위가
곱으로 는다.

## Data contract (새 데이터 이동 도입 시 최소 항목)

dataset 이름·owner / 원천(테이블)·primary key·변경 식별 방식(updated_at 등)
/ 중복 가능 여부·순서 보장 / 스키마 호환 규칙(destructive 변경은 마이그레이션
필수) / 품질 규칙(유니크·not null·값 범위) / PII 여부·보존 기간.

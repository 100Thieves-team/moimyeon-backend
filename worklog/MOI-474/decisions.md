# MOI-474 하네스 구축 — 의사결정 기록

각 결정은 유효한 동안만 살아 있다. 뒤집히면 해당 섹션을 superseded 처리하거나 삭제한다.
일반화 가치가 있는 결정은 완공 시 docs/knowledge/로 승격한다.

## DR-001: 하네스는 레포에 커밋되는 파일로만 구성한다

- 날짜: 2026-08-19
- 상태: 승인

### 결정

하네스(에이전트 정의·스킬·라우팅·산출물 계약)는 전부 저장소에 커밋되는 파일로 구성한다.
특정 런타임에서만 동작하는 프리미티브(Claude session team 등)에 의존하는 구조는 만들지 않는다.

### 근거

- 하네스 엔지니어링의 정의 자체가 "모델 바깥의 환경을 저장소에 남는 파일로 설계하는 것"이다.
  파일이면 런타임(Claude Code, Codex CLI)을 바꿔도 설계물이 이식된다. (하네스 책 ch1)
- 개인 로컬 하네스에 쌓인 지식은 동료에게 전달되지 않는다. 배운 것이 레포를 통해
  선순환해야 팀 하네스다. (멘토링 2026-08-19)
- session team 프리미티브는 토큰 소모가 과해 사용하지 않기로 팀에서 결정했다.

### 대안

- 개인별 `~/.claude` 하네스: 지식이 개인에 고립되어 기각.
- 런타임 팀 프리미티브 기반 설계: 이식성·토큰 문제로 기각.

### 영향

- 모든 하네스 산출물은 PR 리뷰 대상이 된다.
- 런타임별 차이는 symlink 계층(DR-002)에서만 흡수한다.

## DR-002: 단일 소스는 `.agents/`, 런타임 디렉토리는 symlink

- 날짜: 2026-08-19
- 상태: 승인

### 결정

스킬과 에이전트 정의의 단일 소스는 런타임 중립 디렉토리 `.agents/`다.

```
.agents/
├── skills/   # 스킬 단일 소스
└── agents/   # 에이전트 역할 계약 단일 소스

.claude/skills → ../.agents/skills   (symlink)
.claude/agents → ../.agents/agents   (symlink)
.codex/skills  → ../.agents/skills   (symlink)
```

### 근거

- SKILL.md는 오픈 표준이라 같은 파일이 Claude Code와 Codex CLI 양쪽에서 동작한다.
  Codex CLI는 프로젝트 레벨 `.codex/skills/`를 네이티브로 읽는다.
- 복사본이 존재하면 반드시 어긋난다. 실제로 Claude→Codex 포팅 과정에서 스킬이
  변질된 사고가 있었다(멘토링 2026-08-19). symlink면 포팅 drift가 구조적으로 불가능하다.
- 이 레포는 이미 `AGENTS.md`(소스) ← `CLAUDE.md`(symlink) 방향을 쓰고 있다.
  중립 이름이 소스, 런타임 이름이 별칭이라는 같은 원칙을 디렉토리에도 적용한다.

### 대안

- `.claude/skills/`를 소스로, `.codex/skills`만 symlink: 특정 런타임에 소스가
  묶여 위 원칙과 어긋나 기각.
- 각 런타임 디렉토리에 복사: drift 사고 재발 경로라 기각.

### 영향

- 스킬·에이전트 파일 수정은 `.agents/` 아래에서만 한다.
- 런타임이 추가되면 symlink 한 줄로 대응한다.
- Windows 환경은 symlink 지원이 제한적이나 현재 팀은 전원 macOS라 문제없다.

### 검증 (2026-08-19)

`.agents/skills/`에 임시 스킬을 놓고 양 런타임에서 발견 여부를 확인했다.

- Claude Code: 세션 스킬 목록에 등장 — `.claude/skills` symlink 발견 확인.
- Codex CLI 0.148.0: `codex exec` 스킬 목록에 등장 — `.codex/skills` symlink 발견 확인.

## DR-003: 스킬은 지식 문서를 복사하지 않고 경로로 참조한다

- 날짜: 2026-08-19
- 상태: 승인

### 결정

스킬은 `docs/conventions/`·`docs/knowledge/`의 내용을 본문에 복사하지 않는다.
"구현 전 `docs/conventions/layers.md`를 읽어라"처럼 경로만 가리킨다.

두 위치의 역할 구분:

| | `docs/conventions·knowledge` | 스킬 `references/` |
| --- | --- | --- |
| 담는 것 | 팀이 합의한 규칙·경험 (무엇이 올바른가) | 해당 절차 수행의 세부 (어떻게 작업하는가) |
| 독자 | 사람 + 모든 에이전트 | 그 스킬을 실행 중인 에이전트만 |
| 판정 기준 | 스킬을 지워도 팀에 유효하면 여기 | 스킬과 함께 없어져도 되면 여기 |

### 근거

- 같은 내용이 두 곳에 있으면 문서 갱신 시 스킬도 고쳐야 하고, 잊으면 어긋난다.
  실제로 이 문제 때문에 knowledge 폴더를 레포에서 뺐던 경험이 있다(멘토링 2026-08-19).
- 컨벤션 문서는 하네스 도입 과정에서 유실·변경되면 안 된다는 제약이 있다.
- 스킬 본문은 라우터로 얇게 유지하고 상세는 조건부 로드한다는 progressive disclosure
  원칙과도 일치한다. (하네스 책 ch5)

### 대안

- 컨벤션을 스킬 references/로 이관: 문서가 스킬 전용물이 되어 사람·타 에이전트의
  접근성이 나빠지고, "이동 중 유실 금지" 제약 위반 위험이 있어 기각.

### 영향

- 컨벤션 변경은 `docs/`에서만 일어나고 스킬은 수정이 불필요하다.
- 스킬 작성 시 인용이 필요하면 링크로 대체한다.

## DR-004: 라우팅은 AGENTS.md 인덱스로, 등록은 오케스트레이터만

- 날짜: 2026-08-19
- 상태: 승인 (등록 자체는 하네스 완성 시점에 수행)

### 결정

스킬의 자발적 트리거에 의존하지 않는다. 항상 로드되는 `AGENTS.md`에
"백엔드 개발 작업 요청 시 backend-orchestrator 스킬을 사용하라" 한 줄의
라우팅 규칙과 하네스 포인터(목표·트리거·변경 이력)를 등록한다.
개별 워커 스킬 목록은 AGENTS.md에 적지 않는다.

### 근거

- 스킬 자발 호출은 신뢰할 수 없다: Vercel 실험에서 스킬 미호출 56%,
  항상 로드되는 문서 인덱스는 통과율 100% vs 스킬 53%.
  (vercel.com/blog "AGENTS.md outperforms skills", 2026-01)
- 명시적 라우팅 지시가 있으면 호출률이 95%+로 회복된다. (같은 실험, LangChain
  "Evaluating Skills")
- 반대로 CLAUDE.md에 에이전트·스킬 전체 목록을 복사하면 파일과 기록이 어긋나는
  구조 drift가 시작된다. 포인터는 최소 4항목(이름·목표·트리거·변경 이력)만.
  (하네스 책 ch10)

### 대안

- 스킬 description만으로 트리거: 위 수치로 기각.
- AGENTS.md에 전체 스킬 표 등록: drift + 유사 description 간 트리거 경쟁으로 기각.

### 영향

- 워커 스킬은 오케스트레이터가 명시 경로로 호출한다(DR-008).
- AGENTS.md 갱신은 하네스 변경 이력 기록과 함께만 일어난다.

## DR-005: 실행 모델은 서브에이전트 단발 위임 + 파일 계약

- 날짜: 2026-08-19
- 상태: 승인

### 결정

멀티에이전트 실행은 "메인 세션이 서브에이전트를 단발 위임하고, 산출물은
worklog 파일 계약(DR-007)으로 주고받는" 모델로 한정한다.
런타임의 팀 프리미티브(session team, 에이전트 간 실시간 메시징)는 쓰지 않는다.

모든 생성-검증 루프에는 재시도 상한과 종료 조건을 명시한다:

- AI 리뷰 반영: 2회
- 테스트 실패 수정: 3회
- 리뷰봇 커멘트 대응: 2회
- 상한 도달 시: 실패 상태를 worklog에 명시하고 사람에게 에스컬레이트한다.
  조용히 계속 시도하거나 조용히 포기하지 않는다.

### 근거

- 우리 워크플로우 4종은 모두 강한 순차 의존이고 에이전트 간 실시간 협상이
  필요 없다. 서브에이전트 판별 신호(산출물 독립·충돌 낮음·피드백 루프 없음)에
  부합한다. (하네스 책 ch9)
- 팀 모드가 주는 것 중 산출물 인계·상태·경계 계약은 파일로 대체 가능하다.
  대체가 성립하려면 파일 계약이 명시적이어야 한다 → DR-007. (같은 장)
- 재시도 상한 없는 검증 루프는 무한 루프 또는 조용한 품질 저하로 끝난다.
  상한+에스컬레이트는 필수 제한이다. (하네스 책 ch8)
- 3주 세션 데이터에서 상위 세션의 90.5%가 이미 위임 패턴을 쓰고 있었다.
  (workflow_analysis, 2026-08)

### 대안

- session team: 토큰 소모·런타임 종속으로 기각 (DR-001).
- 위임 없이 단일 컨텍스트로 전부 수행: 긴 워크플로우에서 컨텍스트 오염과
  품질 하락(실행 drift)을 초래해 기각.

### 영향

- 오케스트레이터와 workflow 문서는 "어느 단계를 메인이 하고 어느 단계를
  위임하는지"를 명시해야 한다.
- 순서 의존은 파일 존재 확인으로 표현한다(A의 산출물 파일이 있어야 B 시작).

## DR-006: 작업 산출물은 worklog/에 커밋, _workspace/는 개인 스크래치

- 날짜: 2026-08-19
- 상태: 승인

### 결정

- 작업 산출물(계획·결정·TBD 기록)은 `worklog/{이슈키}/`에 저장하고 커밋한다.
- `_workspace/`는 gitignore를 유지하고 개인 스크래치 전용으로 남긴다.
- worklog는 어떤 항상-로드 경로(AGENTS.md 등)에도 연결하지 않는다.
  해당 이슈를 작업할 때만 온디맨드로 읽는다.
- 정리 규칙: 이슈가 머지되고 일반화할 가치가 있는 내용은 `docs/knowledge/`로
  승격한 뒤, 오래된 worklog 디렉토리는 삭제할 수 있다. 정교한 GC 정책은
  운영 경험이 쌓인 뒤 정한다.

### 근거

- 산출물은 작업을 명확히 하고, 인지 부채를 줄이고, 타인에게 컨텍스트를
  공유하기 위한 것이다. 커밋되지 않으면 마지막 목적이 죽는다.
  (팀 워크플로우 정리 문서, 2026-08)
- 단, 플랜·리포트 파일이 상시 로드 경로에 쌓이면 컨텍스트를 잠식한다.
  갱신 안 된 문서는 즉시 지우는 가비지 컬렉션이 가장 중요하다.
  (멘토링 2026-08-19) → "커밋하되 자동 로드에서 격리"로 두 요구를 모두 만족.

### 대안

- 산출물 gitignore 유지(현행): 팀 공유·승격 경로가 없어 기각.
- docs/ 하위에 저장: 큐레이션된 지식과 원시 작업 기록이 섞여 기각.

### 영향

- `.gitignore`의 `_workspace/`는 유지, `worklog/`는 커밋 대상.
- worklog가 재실행 분기(이어하기)의 상태 저장소 역할을 겸한다(DR-007, DR-009).

## DR-007: worklog 파일 계약

- 날짜: 2026-08-19
- 상태: 승인

### 결정

`worklog/{이슈키}/`의 파일명과 역할을 고정한다.

| 파일 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `plan.md` | 승인된 계획 + 체크포인트 체크박스 (진행 장부) | 계획 승인 시 생성, 체크포인트 통과마다 갱신 |
| `context.md` | 수집한 컨텍스트: 이슈 요약, PRD 링크·발췌, 관련 코드 위치 | 컨텍스트 수집 단계 |
| `decisions.md` | 구현 중 내린 결정과 이유 | 결정이 생길 때마다 |
| `tbd.md` | 미결정 사항, PRD·정책서에 반영해야 할 모호점 | 발견 시 |

- 파일이 필요 없으면 만들지 않는다(빈 파일 금지). `plan.md`만 필수다.
- 서브에이전트에 위임할 때 입출력은 이 파일들의 경로로 지정한다.

### 근거

- 팀 프리미티브 없이 서브에이전트+파일로 협업하려면 파일 계약이 곧
  통신 프로토콜이다. 경로·형식이 고정되지 않으면 대체가 성립하지 않는다.
  (하네스 책 ch4 입출력 프로토콜, ch6 경계면 계약)
- 파일명이 고정돼야 재실행 시 "무엇이 이미 됐는지"를 기계적으로 판별할 수 있다.
  (하네스 책 ch10 재실행 지원)

### 대안

- 자유 형식 산출물: 세션·사람마다 달라져 재실행 분기와 위임 입출력이
  성립하지 않아 기각.

### 영향

- 워크플로우 스킬들은 이 파일명을 하드코딩해서 읽고 쓴다.
- 계약 변경은 이 DR 갱신 + 스킬 일괄 수정으로만 한다.

## DR-008: 에이전트/스킬/오케스트레이터 3분법 매핑

- 날짜: 2026-08-19
- 상태: 승인

### 결정

| 책임 | 위치 | 담는 것 |
| --- | --- | --- |
| 오케스트레이터 (언제·누구와) | `.agents/skills/backend-orchestrator/` — 특수 스킬 1개 | 작업 유형 판별, 워크플로우 호출 순서, 체크포인트 정지(DR-009), 실패 정책(DR-005), 재실행 분기 |
| 스킬 (어떻게) | `.agents/skills/` 워커 6개: `requirement-implementation` · `api-spec-definition` · `api-connection` · `entity-design` · `issue-context` · `ship-pr` | 각자 자기 절차만. 본문 체크리스트(≤150줄) + `references/` 상세 |
| 에이전트 (누가) | `.agents/agents/` 역할 계약 (첫 번째: `code-reviewer`, 읽기 전용) | 역할, 판단 기준, 입출력 프로토콜, 에러 핸들링 |

- AGENTS.md 라우팅에는 오케스트레이터만 등록한다(DR-004).
  워커 스킬은 오케스트레이터가 명시 경로로 호출한다.
- 공통 단계(이슈·PRD 수집, 커밋·PR·리뷰봇 대응)는 `issue-context`·`ship-pr`로
  추출한다. 워크플로우 정의상 4개 워크플로우가 도입부·종결부를 공유함이
  이미 확인돼 있으므로 미리 추출한다.
- `entity-design`은 절차가 짧아 스킬 가치가 불확실하다. 작성 후 With/Without
  비교로 유지 여부를 결정한다.

### 근거

- 역할·판단 기준 → 에이전트, 절차 → 스킬, 순서·실패 정책 → 오케스트레이터라는
  판별 기준. (하네스 책 ch3)
- 워크플로우 전 과정을 스킬 하나에 담으면 500줄 한계 초과가 예정되고(ch5),
  전부 한 폴더("workflows")에 뭉치면 오케스트레이터와 스킬의 책임이 섞인다
  — 두 안 모두 검토 후 기각했다.
- 진입점이 오케스트레이터 하나이므로 스킬이 6+1개여도 트리거 오선택 표면은
  늘지 않는다. (LangChain "Evaluating Skills"의 오선택 관찰과 정합)

### 대안

- 워크플로우당 대형 스킬 4개 (v0.1): 크기 초과 + 공통부 4중 복제로 기각.
- 단일 가방 스킬 `backend-workflows` (v0.2): 책임 혼합 안티패턴으로 기각.

### 영향

- 새 워크플로우 추가 = 워커 스킬 1개 추가 + 오케스트레이터 판별표 1행 추가.
- 스킬 이름은 능력을 그대로 서술한다. 내용물 목록형 이름("workflows" 등) 금지.

## DR-009: 체크포인트 실행 프로토콜

- 날짜: 2026-08-19
- 상태: 승인

### 결정

- 각 workflow 문서는 단계 중 사람 검토가 필요한 지점에 `[체크포인트]`를 표시한다.
- 오케스트레이터는 체크포인트에서 **턴을 끝내고** 산출물을 제시한 뒤 승인을
  기다린다. 승인 없이 다음 단계로 넘어가지 않는다.
- 기본값은 체크포인트 ON. 사용자가 "끝까지 진행해" 등으로 명시하면 해제한다.
- 진행 상태는 `worklog/{이슈키}/plan.md`의 체크박스로 기록한다.
  새 세션(다른 사람·다른 런타임 포함)은 plan.md를 읽고 마지막 승인 지점부터
  이어간다.

### 근거

- 텍스트 단계에서 고치는 것은 싸고, 구현 후 고치는 것은 비싸다. 계획이
  승인될 때까지 구현을 시작하지 않는 계획 우선 워크플로우가 실무에서
  검증돼 있다. (멘토링 2026-08-19)
- 한 턴에 많은 작업을 진행하지 않고 설계-검토 사이클로 진행하는 것이
  이 팀의 확립된 작업 방식이다.
- 단계별 정지를 스킬 분할로 구현하면 능력이 아닌 턴 경계 기준의 분할이 되어
  3분법 판별 기준(ch3)에 어긋난다. 정지는 오케스트레이터의 실행 정책이다.

### 대안

- 단계마다 스킬로 분할: 위 이유로 기각.
- 체크포인트 없이 전 과정 자동 진행: 구현 후 수정 비용 폭증으로 기각.
  단, 사용자 명시 해제는 허용(작고 명확한 작업).

### 영향

- plan.md(DR-007)가 체크포인트 장부를 겸한다.
- 워크플로우 소요 턴 수가 늘어나는 대신, 각 턴의 검토 범위가 작아진다.

## DR-010: 하네스 상태는 산출물 자체가, 결정 기록은 worklog가 담는다

- 날짜: 2026-08-21
- 상태: 승인

### 결정

- 별도의 `docs/harness/` 허브를 두지 않는다.
- 하네스의 **상태**는 산출물 자체가 말한다: 스킬 frontmatter, 에이전트 정의,
  hook 설정, AGENTS.md 포인터. 이를 요약·복제하는 상태 문서를 만들지 않는다.
- 하네스 구축 과정의 **의사결정**은 이 작업의 이슈(MOI-474) worklog에 기록한다
  — 다른 모든 이슈 작업과 같은 계약(DR-007)을 따른다.
- 아키텍처 도면과 최소 개요만 `.agents/README.md`에 둔다(단일 소스 디렉토리가
  자기 자신을 설명).

### 근거

- 하네스 구축도 이슈 단위 작업이다. 자신이 정한 산출물 계약(DR-006, DR-007)을
  스스로 따르지 않으면 계약의 신뢰가 깨진다.
- 구조를 문서로 복제하면 파일과 기록이 어긋나는 구조 drift가 시작된다.
  (하네스 책 ch10 — CLAUDE.md에 목록을 복사하지 말라는 것과 같은 원리)
- 저장소에서 추론 가능한 내용의 중복 문서는 비용만 늘린다.
  (arXiv "Evaluating AGENTS.md" 2026-02, 멘토링 2026-08-19의 GC 원칙)

### 대안

- `docs/harness/` 허브 유지(초기안): 위 이유로 기각. DR-001~009는 이 파일로
  이관했고 허브는 삭제했다.

### 영향

- 완공(Step 6) 시 일반화 가치가 있는 결정은 docs/knowledge/로 승격한 뒤
  이 worklog는 GC 대상이 될 수 있다.
- 로드맵·체크포인트는 worklog/MOI-474/plan.md가 담는다.

## 구현 결정 (4단계, 로깅 계약)

| # | 결정 | 이유 |
| --- | --- | --- |
| I1 | Writer는 고정 표식 message(`growth.event`)와 payload로 엔트리를 넘기고, Sanitizer가 표식과 타입이 모두 맞을 때만 그로스로 출력한다. 출력 `message`는 사건명으로 바꾼다 | `RequestLogEntry` 선례. 사건명만 흉내 낸 일반 로그가 그로스로 승격되지 않는다 |
| I2 | 별도 `occurredAt` 없이 공통 `timestamp`를 사건 시각으로 쓴다 | 커밋 직후 기록하므로 차이가 작고 필드를 늘리지 않는다 |
| I3 | 사건명은 정확히 두 마디, 속성 값은 Int·Long·Boolean·UUID·enum만(문자열 불가, 리뷰 반영) | 문자열은 형태 검사로 닉네임·전화번호를 거를 수 없다. 분류 값은 enum으로 넘긴다. 숫자에 개인 식별 값을 넣지 않는 것은 5단계 호출 지점 리뷰 항목 |
| I4 | dev 구분은 새 필드 없이 공통 `environment`를 쓴다(D17) | 이미 모든 줄에 있다 |
| I5 | 엔트리는 data class가 아니고 속성 map을 복사해 보관한다. 표식 없이 payload에 들어온 엔트리는 일반 로그에서 버린다(리뷰 반영) | 생성 후 원본 map 변경으로 검증을 우회하거나, 자동 toString으로 analyticsId가 일반 로그에 나가는 것을 막는다 |
| I6 | 속성 키는 `[A-Za-z][A-Za-z0-9_]*`로 기존 필드명 문법보다 좁힌다 | PostHog 속성 이름과 그대로 맞춘다 |
| I7 | 그로스 출력은 표식·타입·INFO 수준이 모두 맞을 때만 한다(QA 참고 3 반영) | 다른 수준으로 남긴 엔트리가 운영 로그 경로에 가명 ID를 남기지 않게 한다 |
| D18 | 국외 이전 약관 내용 | 법률 검토 전 초안(`privacy-policy-draft.md`)으로 v1.0을 넣고, live 정식 출시 전 검토 결과로 새 버전을 낸다 | 2026-10-10 | 필수 약관 행이 있어야 가입 시 자동 동의(D13)가 동작한다 |

## 구현 결정 (5단계, PR 2)

| # | 결정 | 이유 |
| --- | --- | --- |
| I8 | 해시 키가 없으면 `analyticsId`를 null로 두고 기동 시 WARN 한 줄. 필수 설정으로 만들지 않는다 | 키 주입(PR 4) 전 배포에서도 dev가 기동한다. JWT_SECRET처럼 필수로 두면 test·CI·Dockerfile AOT에도 값이 필요해진다 |
| I9 | HMAC 입력은 UUID 16바이트(big-endian), 출력은 앞 16바이트 hex. 고정 기대값 테스트로 계산 방식을 묶는다 | 다른 언어(배치·스크립트)로 같은 값을 재현할 기준 |
| I10 | `seed.sql`의 국외 이전 약관 시행 시각은 2026-07-01, V36은 2026-10-10 | 목록·가입은 모든 종류의 활성 약관을 요구하는데, 로컬·테스트에 2026-10-10 이전으로 고정한 약관 시행 테스트가 있다. 본문은 같다 |
| I11 | V36 기존 회원 일괄 동의는 탈퇴 회원 행도 포함 | 탈퇴 후 복구(MOI-540)되는 회원도 필수 약관 동의 상태를 유지한다 |

참고: 시행 중인 처리방침 v1.1 §12는 "별도 동의가 필요한 새로운 수집·이용·제공은 공지만으로 동의를 대신하지 않는다"고 적는다.
D16(기존 회원 일괄 동의)은 정식 출시 전 내부·테스트 계정만 있다는 전제에서만 맞다. 출시 후 같은 방식으로 약관을 추가하지 않는다.
| I12 | (DB 리뷰 반영) 마이그레이션 IT는 V36 재실행 대신 "같은 약관 행이 이미 있으면 실패하고 아무것도 바꾸지 않음"과 V36 시행 시각을 검증한다 | Flyway 재실행 테스트는 항상 참이라 SQL 안전장치를 검증하지 못한다 |

출시 후 주의(DB 리뷰 참고): 새 약관 종류는 enum을 먼저 배포하고 약관 행을 다음 배포에 넣는다(이전 서버가 모르는 enum을 읽지 않게).
회원 수가 많아진 뒤의 일괄 동의는 마이그레이션과 백필을 나눈다. 탈퇴 회원 동의는 복구 시 `agreeRequired`로 받는다.
| I13 | (컨벤션 리뷰) `AnalyticsIdGenerator`는 `domain/analytics`에 둔다. `MemberService`가 다른 개념의 Generator를 직접 쓰는 것을 받아들인다 | PR 3의 사건 리스너(`core/event`)도 같은 Generator를 쓴다. 회원 개념에 두면 리스너가 회원 Implement를 끌어오게 된다. `withdraw` 흐름도 이미 다른 개념 Implement를 직접 쓴다 |
| I14 | (컨벤션 리뷰) 키는 비었거나 32바이트 이상만 허용 | 짧은 키로 가명 ID를 쉽게 추측할 수 없게 한다. 운영 키는 `openssl rand -hex 32`(64바이트) |
| I15 | (QA 참고) `AnalyticsProperties.toString`은 키를 가린다. 키 앞뒤 공백 처리는 PR 4 주입 때 확인한다 | 설정 덤프 경로가 생겨도 키가 남지 않게 한다 |

QA 조건(PR 2): FE `login-dialog.tsx`는 이용약관·처리방침 링크 2개를 고정 문구로 보여주고 `terms-page.tsx`는 종류를 `SERVICE | PRIVACY`로 고정한다.
새 종류는 화면을 깨지 않지만 국외 이전 약관이 보이지 않은 채 동의가 기록된다. live 전 FE에 국외 이전 약관 링크·페이지 추가가 필요하다(PR 본문 FE 전달 사항).
전송(PR 4)은 탈퇴 삭제(PR 5)와 함께 live에 올린다. 약관 본문이 "탈퇴하면 이전된 기록도 삭제"를 약속한다.

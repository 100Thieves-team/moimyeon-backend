# PDFBox 한글 텍스트 추출 검증

검증일: 2026-09-03

## 전제

- OCR은 지원하지 않는다.
- PDF 원본을 LLM에 보내는 fallback은 사용하지 않는다.
- 추출 정확성을 증명할 수 없는 문서는 보수적으로 거부한다.
- PDFBox에는 공식 추출 confidence/accuracy 지표가 없다. `Preflight`는
  PDF/A 구조 검증이며 화면과 추출 문자열의 의미 일치를 보증하지 않는다.

## 합성 PDF 실험

렌더링으로 보이는 문자열을 확인한 뒤 PDFBox 3.0.7의 기본 content-stream
순서와 `sortByPosition=true` 순서를 각각 추출했다.

| 픽스처 | 렌더링 | content-order | position-order | 판정 |
| --- | --- | --- | --- | --- |
| ReportLab 선형 한글 | 정상 | 정답 일치 | 정답 일치 | 허용 가능 |
| ReportLab 2열 한글 | 정상 | 왼쪽 열 전체 뒤 오른쪽 열 | 같은 높이의 좌·우 열을 한 줄로 합침 | 순서 모호, LLM 해석 전제로 허용 |
| ReportLab 분리 자모 | 화면부터 자모가 분리됨 | NFD 자모 유지 | NFD 자모 유지 | NFC 정규화 후 허용 |
| LibreOffice 표 한글 | 정상 | `프로/젝트`, `주문/서비/스`로 분리 | 열 내용까지 한 줄로 합침 | 단어·순서 손상, LLM 해석 전제로 허용 |

## 확인된 사실

- `sortByPosition=true`가 항상 더 정확하지 않다. 2열 문서에서는 서로 다른
  열을 행 단위로 합칠 수 있다.
- NFC 여부만으로는 충분하지 않다. LibreOffice 표 결과는 NFC지만 단어와
  열 관계가 손상됐다.
- 두 추출 순서가 동일한 선형 문서는 가장 높은 신뢰도로 처리할 수 있다.
- 두 결과가 다르면 어느 쪽이 시각적 의미와 같은지 OCR 없이 자동 판정할 수
  없다.

## 실서비스에 적용할 결정적 통과 조건

다음 조건을 모두 충족한 PDF만 LLM 입력으로 사용한다.

1. PDF 파싱과 텍스트 추출에 성공한다.
2. 추출 문자열이 비어 있지 않다.
3. 아이콘 폰트의 Private Use 문자는 공백으로 제거하고, U+FFFD·NUL·허용하지
   않는 제어문자가 없음을 확인한다.
4. 추출 문자열을 NFC로 정규화한다.
5. 이미지 전용·암호화·손상 PDF는 거부한다.
6. 50페이지 또는 추출 문자열 60,000자를 초과하면 거부한다.
7. 위치 기준으로 정렬하고 표·2열의 줄·순서 변화는 LLM이 문맥으로 해석하게 한다.

실험 후 사용자가 실서비스 수용성을 우선하기로 결정해 content-order와
position-order의 일치 강제, glyph 매핑 100% 같은 엄격한 조건은 제외했다.

## 테스트 스펙

- 선형 한글·영문·숫자·기호 PDF는 정답 문자열 그대로 추출한다.
- 화면 위치 순서로 텍스트를 추출한다.
- NFD 한글은 NFC로 정규화하고 Private Use 문자는 제거한다. 대체문자와
  허용하지 않는 제어문자는 거부한다.
- 이미지 전용·빈 텍스트·암호화·손상 PDF는 거부한다.
- 51페이지·60,001자 PDF는 CI 단위 테스트에서 거부를 검증한다.
- 거부된 PDF는 Bedrock을 호출하지 않고 이력서 요약 실패로 처리한다.

## 남는 한계

잘못된 ToUnicode 매핑이 우연히 정상적인 다른 한글로 연결된 경우는 OCR 없이
탐지할 수 없다. 표·다단의 의미 연결도 모델 판단에 남는다. 사용자는 이 두
위험을 실서비스에서 수용하기로 결정했다. 문자 상한은 `TextPosition` 수집
시점에 중단하지만, 거대한 단일 압축 문자열을 그 이전에 해제하는 PDFBox 내부
임시 메모리까지 하드 제한하지는 못한다.

# MOI-594 결정 기록

## D-1: "준비됨"은 소비 주기 하나가 끝까지 돈 것

- Worker는 HTTP 서버가 없다. 소비 주기(Pending 회수 + 새 메시지 소비)가 예외 없이 끝날 때마다 하트비트 파일
  (`/tmp/core-worker-heartbeat`)을 갱신하고, ECS 컨테이너 상태 검사가 5분 안에 갱신됐으면 HEALTHY로 본다.
  Redis 연결과 Consumer Group이 살아 있어야 주기가 끝난다.
- ECS는 상태 검사가 있으면 HEALTHY가 된 태스크만 배포 완료로 세고, 실패하면 배포 circuit breaker가 되돌린다.
  그래서 "소비 루프가 뜨지 않았는데 배포가 성공으로 끝나는" 경우가 사라진다.
- 시작 유예 180초: AOT 캐시 기동, MySQL 첫 연결(10초 허용), Consumer Group 생성, 첫 주기(초기 지연 5초)를 넉넉히 덮는다.
- 5분 기준: 한 주기는 보통 1초 간격이지만 배치(10건)의 외부 전송이 오래 걸릴 수 있다. 5분 넘게 주기가 끝나지 않으면
  멈춘 것으로 보고 ECS가 교체한다. Redis가 5분 넘게 끊기면 Worker가 재시작되지만, 소비 상태는 Redis에 있어 잃지 않는다.
- 하트비트 쓰기 실패는 소비를 멈추지 않는다(경고만). 계속 실패하면 상태 검사가 교체한다.
- 경로는 Terraform이 환경변수로 주고 같은 값을 상태 검사 명령에 쓴다(앱 기본값도 같음).

## D-2: 교체 중 공백은 허용하고 정상 비율은 0%로 둔다

- 이슈의 [결정 필요]에 대한 답: 공백 허용, 최소 정상 비율 0%.
- 이유: 비율을 올리면 교체 중 Worker 2개가 동시에 떠야 하는데, 여유 용량 부족으로 교체 태스크가 뜨지 못한 장애가 있었다.
  MOI-590(#191)이 머지되면 Worker 교체 자체가 크게 준다(최근 배포의 약 절반이 불필요한 교체였다). 공백 동안의 메시지는 Redis Stream에
  남아 새 Worker가 처리한다(유실 없음, 지연만).
- 비율을 올리려면 먼저 ECS 용량(인스턴스 여유)을 확인해야 한다. 이번 범위에서 바꾸지 않는다.

## D-3: 리뷰 반영(qa-reviewer CONDITIONAL)

- live 승격·롤백이 쓰는 안정 대기(`lib/ecs-stable-wait.sh`)가 배포 1개·실행 수만 보고 상태 검사 전에 성공으로 끝날 수 있었다.
  PRIMARY 배포의 `rolloutState`가 COMPLETED일 때만 성공으로 본다(값이 없으면 이전과 같다). dev 배포 대기는 이미 COMPLETED를 본다.
- FCM 클라이언트의 연결·읽기 시간 제한을 10초로 명시했다. 정하지 않으면 SDK 기본값을 따라 느린 응답이 소비 주기를 붙잡아
  5분 기준을 넘길 수 있다. SDK 자체 재시도(503·Retry-After)가 길어지는 경우는 남는 위험이다.
- MOI-590의 Worker 교체 판단은 원본 틀을 비교하므로, 이 변경처럼 Worker 원본 틀만 바뀐 커밋도 교체로 판정된다(#191 테스트).
- 실패할 때 걸리는 시간: 하트비트가 끝내 안 써지면 태스크 하나당 기동+180초+3×30초 ≈ 5분, circuit breaker가 멈추는 3회면 약 15분이다.
  dev 배포 대기 기한(1500초) 안이지만 인스턴스 증설이 겹치면 FAILED 대신 시간 초과로 끝날 수 있다(결과는 같은 실패).
- 남는 위험: Redis가 5분 넘게 끊기면 Worker가 약 5분 간격으로 재시작되고, 최대 200% 설정 때문에 대체 태스크가 먼저 뜨려고 해
  Worker 2개분 용량을 요구할 수 있다. 실제 동작은 dev에서 관찰해 operations.md에 남긴다.

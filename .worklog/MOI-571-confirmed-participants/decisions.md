# MOI-571 결정 기록

## 확정 명단은 완료 검증과 같은 조회를 재사용한다
- 날짜: 2026-10-06
- 내용과 이유: 명부의 `confirmedParticipants`를 `ParticipationFinder.getConfirmedParticipantIds`(최신 CONFIRMED 로그 기준)에서 만든다. 화면이 받은 명단과 완료 API가 대조하는 명단이 같은 식에서 나와야 E1706이 재발하지 않는다.
- 대안: 별도 출석 대상 API — 이슈 계약이 기존 응답 확장을 택했다.

## 현재 명단과 확정 명단을 별도 배열로 두고 memberId·nickname 중복을 허용한다
- 날짜: 2026-10-06 (구현 리뷰 중 사용자 확인)
- 내용과 이유: 확정 후 이탈이 없으면 두 배열에 같은 사람이 들어가 memberId·nickname이 두 번 나간다. 프론트가 출석 명단을 그대로 받아 완료 API에 보내는 형태를 요청했고, 화면이 명단을 다시 조합하지 않아야 E1706 재발을 막는다. 정원 상한이 8명이라 중복은 몇 줄 수준이다.
- 대안: participants에 출석 대상 표시 + 이탈자만 별도 배열 — 화면이 두 목록을 합쳐야 한다. 이탈자를 participants에 상태로 섞기 — 현재 참여자 명단과 이력서 권한의 의미가 깨진다. memberId만 주기 — 이탈자의 닉네임을 표시할 수 없다.

## 탈퇴한 확정 참여자의 닉네임은 "탈퇴한 회원"으로 채운다
- 날짜: 2026-10-06 (계획 승인 때 확정)
- 내용과 이유: 기존 명부의 대체 문구(`WITHDRAWN_PARTICIPANT_NICKNAME`)와 맞춰 응답 필드를 non-null로 유지한다. 출석 다이얼로그가 빈 이름을 따로 처리하지 않아도 된다.
- 대안: nullable 닉네임 — 프론트 분기만 늘린다.

## 확정 명단은 확정 당시 참여 순서로 정렬한다
- 날짜: 2026-10-06 (계획 승인 때 확정)
- 내용과 이유: 완료 검증 조회가 돌려주는 순서(합류 시각·id 오름차순)를 그대로 쓴다. 방장을 맨 앞으로 올리지 않는다.
- 대안: 현재 명부처럼 방장 우선 — 확정 명단에는 방장 여부 필드가 없어 정렬 기준이 드러나지 않는다.

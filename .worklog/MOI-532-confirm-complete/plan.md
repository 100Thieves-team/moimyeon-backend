# MOI-532 구현 계획

## 자연어 흐름

방장이 모집 중 룸의 진행을 확정하면 서버는 기존과 동일하게 룸 행을 잠그고 방장 권한,
최소 진행 인원, 일정 조건을 검증한다. 성공하면 확정 참여자 스냅샷의 기준이 되는
`CONFIRMED` 전이 이력을 남긴 뒤 룸의 최종 상태를 즉시 `COMPLETED`로 만든다. 같은 시각과
처리자를 사용한 `COMPLETED` 전이 이력을 남기며, 확정 참여자 전원을 `ATTENDED`로 기록한다.
남은 대기 신청은 기존과 같이 `ROOM_CONFIRMED`로 종료한다. 이 쓰기들은 하나의 트랜잭션으로
커밋되거나 모두 롤백된다.

## 구현 접근

- `RoomEntity`에 확정과 즉시 완료를 하나의 의도로 표현하는 전이 메서드를 둔다.
  - 시작 상태는 `RECRUITING`, 종료 상태는 `COMPLETED`다.
  - `IN_PROGRESS` 상태를 설정하지 않는다.
  - 기존 `confirm/startProgress/complete` 메서드는 기존 진행 흐름과 테스트 호환을 위해 유지한다.
- `RoomManager.confirm`은 기존 조건 검증 뒤 직접 완료 전이를 호출한다.
- 같은 `now`와 방장 id로 `CONFIRMED`, `COMPLETED` 상태 로그를 모두 저장한다.
  - `CONFIRMED` 로그: 참여자 확정 시점 스냅샷 계약 유지.
  - `COMPLETED` 로그: 현재 상태와 종료 시각·처리 주체의 일치 보장.
- 대기 신청 종료 순서와 상태(`ROOM_CONFIRMED`)는 유지한다.
- 룸 행 잠금 안에서 조회한 현재 `JOINED` 참여자 전원에게 출석을 생성한다.
  - 상태: `ATTENDED`
  - 기록자: 확정을 실행한 방장
  - 기록 시각: 두 상태 로그와 같은 `now`
  - 확정 조건의 인원수와 출석 대상이 갈리지 않도록 동일한 참여자 목록을 사용한다.
- 확정 API의 RestDocs 설명을 `RECRUITING → COMPLETED`와 우회되는 단계가 드러나도록 수정한다.
- API URI·응답 형태·오류 코드는 변경하지 않는다.

## 테스트 스펙

- `RoomManagerTest`
  - 조건을 충족한 확정 요청의 최종 상태가 `COMPLETED`다.
  - 최소 인원 경계에서도 직접 완료된다.
  - `CONFIRMED`와 `COMPLETED` 로그가 같은 처리자·시각으로 각각 한 번 저장된다.
  - 확정 참여자 전원에게 `ATTENDED` 출석이 같은 기록자·시각으로 저장된다.
  - 대기 신청 종료가 기존 값으로 호출된다.
  - 조건 실패 시 룸 상태와 부수효과가 변경되지 않는다.
- `RoomConfirmationIT`
  - 최종 DB 상태 `COMPLETED`, 두 상태 로그, 전원 출석, 대기 신청 종료가 한 커밋으로 남는다.
  - `CONFIRMED` 로그를 이용한 확정 참여자 조회가 직접 완료 뒤에도 유지된다.
  - 재요청은 기존 `E1410`이고 두 전이 로그와 신청 종료가 중복되지 않는다.
  - 후속 쓰기 실패 시 상태와 두 로그, 신청 변경이 모두 롤백된다.
- `RoomControllerTest`
  - 성공 계약은 유지하고 문서 설명만 새 상태 흐름으로 갱신한다.
- 회귀 검증
  - 기존 진행 시작·클로징·자동 완료 경로의 단위/통합 테스트를 실행한다.
  - 전체 `test`, `ktlintCheck`, `restDocsTest`를 실행한다.

## 영향과 의도적 비범위

- 직접 완료된 룸은 면접 현황에서 완료 목록으로 이동하고 활성 룸·참여 슬롯을 즉시 해제한다.
- 원본 이력서 열람 창은 완료 상태 정책에 따라 즉시 닫힌다.
- 확정 참여자 전원을 `ATTENDED`로 보므로 직접 완료 뒤 후기 작성 자격과 신뢰 통계에 반영된다.
- 진행 시작 API 제거, DB enum/스키마 변경, 기존 진행 중 룸의 마이그레이션은 범위 밖이다.

# MOI-590 결정 기록

## D-1: 판단 기준은 산출물 입력과 태스크 정의 원본 틀

- 이슈의 [결정 필요] "판단 기준"에 대한 답: 파일 경로나 Gradle 의존 그래프가 아니라 산출물 비교.
  - 이미지 입력 해시 = sha256(core-worker boot jar, Dockerfile, Dockerfile.dockerignore). PR CI와 대체 빌드가 이미지 label
    `org.moimyeon.runtime-input`으로 붙이고, PR CI는 올린 직후 실제 ECR에서 다시 읽어 확인한다.
  - boot jar는 재현 가능해서(MOI-588에서 clean 재빌드 jar 해시 동일 확인) 공유 모듈·의존성 버전이 바뀌면 해시가 바뀌고, 안 바뀌면 같다.
    경로 목록처럼 공유 모듈을 빠뜨릴 위험이 없다.
  - 이미지 digest는 쓰지 않는다. AOT 캐시 학습 결과가 빌드마다 달라질 수 있다.
  - 태스크 정의: 실행 중인 revision이 지금 Terraform 원본 틀에 이미지·`APP_RELEASE`만 바꾼 것과 같은지 비교한다
    (`prepare_ecs_task.py --compare-running`). 환경변수·시크릿·로그 라우터·크기가 바뀌면 교체한다.
- 일부러 뺀 것: JRE 기반 이미지 태그 갱신, AOT 캐시 내용. 코드가 같으면 Worker를 재시작할 이유가 아니다.

## D-2: 비교 기준은 "지금 실행 중인 Worker"

- 이슈의 [결정 필요] "직전 커밋 / 서비스별 마지막 배포 성공 이후 누적"에 대한 답: 실행 중인 Worker 자체와 비교한다.
  커밋 이력을 보지 않으므로 "API 변경 A 다음 Worker 변경 B"에서 판단이 어긋나는 문제가 없다.
- 확인할 수 없으면 교체한다: 후보 승격이 아님(대체 빌드), 실행 중인 서비스가 교체 중, label 없음(이 변경 전 이미지 포함), 원본 틀 다름.
  그래서 이 변경 뒤 첫 배포는 Worker를 교체하고(이전 이미지에 label이 없음) 그다음부터 유지가 가능하다.

## D-3: 유지한 Worker는 이 커밋의 기록에 이어 적는다

- 실행 중인 revision과 그 이미지를 기록하고, 이미지에 `deployed-dev-<sha12>` 표식을 붙인다(승격·롤백이 표식을 확인한다).
  dev 태스크 정의는 커밋 태그 이미지를 쓰므로 표식 복사 결과(digest)를 기록한다.
- 같은 커밋 재시도(MOI-589)는 이 커밋의 Worker 표식(`deployed-dev-<sha12>`)을 따른다. 표식은 기록보다 먼저 붙으므로
  이전 시도가 무엇을 했는지 알려 준다. 표식이 이 커밋 이미지면 교체(기록이 있으면 기록된 revision), 이전 이미지면
  실행 중 Worker가 그 이미지일 때만 유지하고, 아니면(롤백 뒤 재실행 등) 바꾸기 전에 멈춘다(qa-reviewer 필수 지적 반영).
- live 승격은 이 기록의 Worker(이전 revision의 이미지)를 승격한다. 코드가 같은 이미지라 결과는 같다.

## D-4: 순서와 병렬

- API 먼저, Worker 나중은 그대로다(스키마 마이그레이션은 API가 맡음). 병렬 교체는 하지 않는다.
- 판단은 대체 빌드용 jar 빌드와 서비스 변경 전에 한다. 유지할 때는 Worker 이미지를 빌드·등록·교체하지 않는다.

## D-5: 남는 위험

- 시크릿 값만 바꾸면 Worker가 다시 시작되지 않는다(태스크 정의에는 ARN만 있음). infra.md에 수동 재시작 방법을 적었다.
- label은 PR CI가 계산해 붙인다. CI의 다시 읽기는 "label = 계산한 해시"만 증명한다. 계산이 틀리면 새 Worker 코드가 dev·live에
  배포되지 않을 수 있다. 해시 계산은 jar·Dockerfile만 읽는 짧은 스크립트이고 단위 테스트로 고정했다.
- "안정 상태"는 완료된 배포 하나와 실행 태스크 수가 원하는 수와 같고 대기 태스크가 없을 때다.

## 리뷰 반영(PR #191 다중 에이전트 리뷰)

- 유지 판단과 기록 사이에 API 교체(최대 30분)가 끼므로, 기록 직전에 실행 중 Worker가 판단 때와 같은지 다시 확인하고 다르면 기록하지 않는다.
- 판단을 `decide-worker-change.sh`로 옮기고 가짜 aws·docker로 분기별 실행 테스트를 붙였다(유지, 후보 아님, 만료, 코드 변경, label 없음,
  불안정, 원본 틀 변경, 재시도 교체·유지·중단). 원본 틀만 바뀐 변경(예: Worker 상태 검사 추가, MOI-594)도 교체로 판정된다.
- `worker-scope-test.sh`를 CI build job에 등록했다.

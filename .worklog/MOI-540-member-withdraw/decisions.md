# MOI-540 결정 기록

사람이 대화에서 정한 결정이다. Wiki 반영은 wiki-sync 단계에서 한다.

## 2026-10-02

1. **7일 이력서 삭제·30일 개인정보 마스킹은 이번 범위에서 뺀다.** 정기 작업과 S3 삭제가 필요하고
   서비스 런칭 이후에 개발해도 된다. 후속 이슈 MOI-562로 분리했다.
2. **탈퇴 시 그 회원의 리프레시 토큰을 모두 폐기한다.**
3. **같은 Google 계정으로 다시 로그인하면:** 소프트 삭제된 회원 행이 DB에 있으면 그 계정을 복구하고,
   없으면 새로 가입시킨다. 지금 코드의 재가입 차단(`MEMBER_ALREADY_WITHDRAWN`)과 PRD R89·로그인 게이트를 바꾼다.
4. **탈퇴 작성자 표시 문구는 "탈퇴한 회원"으로 통일한다.** 코드 9곳과 DEC-005가 이미 쓰는 문구다.
5. **룸 나가기의 최소 인원 차단을 없앤다.** 확정 룸에서 방장은 인원과 관계없이 나갈 수 있는데(MOI-541)
   일반 참여자만 막히는 비대칭이다. 참여자가 나가 최소 진행 인원보다 적어지면 방장 이탈처럼
   룸을 모집 중으로 되돌린다. 탈퇴는 이 나가기를 예외 없이 호출한다.
   별도 이슈 MOI-561로 분리하고 스택 PR로 올린다. 순서: MOI-561(base dev) → MOI-540(base MOI-561).
   탈퇴가 바뀐 나가기에 기대므로 나가기 변경이 먼저다.
6. **계정 복구 범위:** 계정·프로필·이력서만 돌아온다. 나간 룸·철회된 신청·폐기된 세션은 되돌리지 않는다.
   이력서는 탈퇴 후 7일 보관이므로 이미 삭제된 이력서는 복구할 수 없다(삭제 자체는 MOI-562).
7. **복구는 확인 단계를 둔다.** 탈퇴한 계정으로 로그인하면 바로 복구하지 않고 사용자가 복구를 확인한다.
8. **탈퇴 상태는 저장하는 상태값이 아니라 탈퇴 시각(코드의 `deleted_at`)에서 계산한다.** 계정 이용 상태는
   `ACTIVE`·`RESTRICTED`만 남긴다. 이용 제한과 탈퇴가 따로 움직여야 탈퇴 후 복구로 제한이 풀리지 않는다.
   상태 SSOT를 코드에 맞춰 고친다.
9. **MOI-561: 참여자 이탈로 모집이 재개되면 방장과 남은 참여자에게 알린다.**
10. **탈퇴는 API 하나에서 활성 룸 나가기·신청 철회까지 자동 처리하고, 탈퇴 전 화면에서 영향을 안내한다.**
    "직접 다 나온 뒤 탈퇴(검사만)" 안과 비교: MOI-561 이후 나가기가 막히는 경우가 없어 룸별 결과가 같고,
    차이는 수고뿐이다. 수고는 이탈 방지 장치(다크 패턴)에 가깝고, 영향 인지는 안내 화면으로 얻는다.
    한 트랜잭션이라 중간 상태·경쟁 상황이 없다. PRD R94·R95와 일치.
11. **진행 예정 시각이 지난 확정 룸은 탈퇴 때 나가지 않는다.** 면접이 이미 열렸을 수 있어 "확정 후 이탈"로 남기면
    사실과 다르다. 참여자로 남아 "탈퇴한 회원"으로 보이고 완료·출석·후기는 평소대로 진행된다(R128과 같은 취지).
12. **탈퇴 API는 `DELETE /v1/members/me`.** "내 것을 없앤다 = DELETE" 관례.
13. **탈퇴 시 웹 푸시 구독을 삭제한다.** 복구하면 다시 구독한다.
14. **복구 확인:** 탈퇴 회원이 로그인하면 세션을 열지 않고 복구 확인 쿠키(10분, HttpOnly, path `/v1/auth`)와 함께
    프론트 복구 확인 화면으로 보낸다. `POST /v1/auth/restoration`이 쿠키를 검증해 복구하고 세션을 발급한다.
15. **탈퇴 직후 액세스 토큰(최대 30분)은 허용한다.** 응답에서 쿠키를 만료시키고 리프레시를 막는다.
    요청마다 회원 조회를 더하지 않는다.
16. **후기 작성 기간 중 탈퇴는 따로 처리하지 않는다.** 쓴 후기·받은 후기는 남고 작성자는 "탈퇴한 회원"으로 보인다.

## 구현 중 결정 (2026-10-02)

17. **탈퇴는 한 트랜잭션으로 묶지 않고 단계마다 커밋한다: 신청 철회 → 룸마다 나가기(기존 나가기 경로) → 회원 정리.**
    한 트랜잭션에서 여러 룸을 차례로 잠그면 MySQL 기본 격리 수준에서 뒤 룸의 조회가 앞서 만든 스냅샷을 봐
    다른 요청이 방금 커밋한 나가기·내보내기를 덮어쓴다(DB·코드 리뷰 필수 지적). 처음에는 READ COMMITTED로 막았으나
    "비즈니스 로직을 위해 격리 수준을 낮추는 것"은 규칙을 설정 한 줄에 숨기고 호출 위치에 따라 조용히 무시되므로 되돌렸다.
    룸마다 따로 커밋하면 각 룸이 사용자가 나가기를 누른 것과 같은 경로(룸 잠금이 첫 쿼리)를 타 별도 장치가 필요 없다.
    잃는 것은 전체 원자성이다. 중간 실패 시 일부 룸만 나간 채 계정이 남지만 각 단계는 정상 상태이고, 다시 요청하면
    남은 룸부터 이어서 끝난다. 회원 정리 커밋 안의 세션 폐기·푸시 삭제·회원 삭제는 함께 묶인다(MemberWithdrawRollbackIT).
18. **방장 자동 위임 후보 신청은 행 잠금으로 다시 읽어 PENDING일 때만 승격한다.** 동시에 탈퇴하는 신청자의 철회를 덮어써
    탈퇴 회원이 방장이 되는 경쟁을 막는다.
19. ~~동시 탈퇴 두 건의 드문 교착~~: 17번으로 룸 처리가 룸 단위 커밋이 되어 여러 룸을 한 트랜잭션에 쥐지 않으므로 해소됐다.
20. **탈퇴는 멱등이다.** 이미 탈퇴한 회원의 재요청은 아무것도 하지 않고 성공한다(SSOT `C.member.withdraw` 멱등 예).
    탈퇴 직후 남은 액세스 토큰으로 버튼을 다시 눌러도 404가 나지 않는다.
21. **탈퇴 처리 전체가 한 시각을 쓴다.** 룸 나가기의 예정 시각 판정도 탈퇴 흐름이 정한 시각으로 한다.
22. **복구 API는 기존 refresh 처럼 AuthController가 직접 조립한다.** layers.md(여러 Service 조합은 Facade)와 어긋나지만
    refresh 가 같은 모양이고 AuthController 이동이 auth.md 미확정 항목이라 이번에 구조를 바꾸지 않는다.
    대신 Implement 직접 호출을 빼고(`memberService.getMember`), 세션 발급은 `SessionIssuer` 포트를 재사용했다.
23. **복구도 멱등이다.** 이미 복구된 회원이 같은 복구 확인 토큰으로 다시 요청하면 로그인만 다시 된다(SSOT `C.member.restore`).
    복구 버튼을 두 번 눌러도 오류가 나지 않는다. 처음 구현의 E1014(탈퇴 상태 아님)는 쓰이지 않게 되어 지웠다.
24. **복구 확인 화면은 프론트 `/auth/restore`로 따로 두고, 주소를 덮어쓰는 환경변수는 두지 않는다.** callback 이 결과별
    분기 허브가 되는 것을 피한다. 기존 성공·실패 환경변수도 인프라에서 설정하지 않아 프로파일별 고정값이면 충분하다.
    프론트 주소 설정을 base URL 하나로 통합하는 정리는 범위 밖(후속 작업 후보)이다.
25. **탈퇴 중 새로 생긴 참여는 회원 정리 단계가 감지해 처음부터 다시 돈다(최대 3번, 실패 시 409 E1014).** 룸을 나가는 사이
    본인이 다른 탭에서 룸을 만들거나 신청이 수락되면 그 룸이 남는다(QA 권고). 회원 정리에서 남은 룸을 직접 나가면 한 트랜잭션에
    여러 룸 잠금이 다시 생기므로, 회원을 잠그고 대기 신청을 닫은 뒤 "앞서 나간 룸 밖의 참여"만 확인해 있으면 회원을
    지우지 않고 돌아간다. 회원 잠금 뒤에는 새 룸 생성·신청이 막히고, 신청을 먼저 닫아야 방장이 수락 중이던 신청의
    잠금을 기다려 그 결과까지 확인에 잡힌다(PR 리뷰 지적으로 순서를 바꿈).

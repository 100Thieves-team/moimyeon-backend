# MOI-474 하네스 구축 — 의사결정 기록

각 결정은 유효한 동안만 살아 있다. 뒤집히면 해당 섹션을 superseded 처리하거나 삭제한다.
일반화 가치가 있는 결정은 완공 시 docs/knowledge/로 승격한다.

## DR-001: 하네스는 레포에 커밋되는 파일로만 구성한다

- 날짜: 2026-08-19
- 상태: 승인

### 결정

하네스(에이전트 정의·스킬·라우팅·산출물 계약)는 전부 저장소에 커밋되는 파일로 구성한다.
특정 런타임에서만 동작하는 프리미티브(Claude session team 등)에 의존하는 구조는 만들지 않는다.

### 근거

- 동작 원리: 두 런타임이 공유하는 기질은 저장소 파일뿐이다. Claude Code는
  `CLAUDE.md`와 `.claude/{skills,agents}`를, Codex CLI는 `AGENTS.md`와
  `.agents/skills`(구버전 별칭 `.codex/skills`)를 읽는다. 런타임 내부 상태
  (세션 메모리, 개인 로컬 설정)는 상대 런타임에도, 팀원에게도 보이지 않는다.
- 하네스 엔지니어링의 정의 자체가 "모델 바깥의 환경을 저장소에 남는 파일로 설계하는 것"이다.
  파일이면 런타임(Claude Code, Codex CLI)을 바꿔도 설계물이 이식된다. (하네스 책 ch1)
- 개인 로컬 하네스에 쌓인 지식은 동료에게 전달되지 않는다. 배운 것이 레포를 통해
  선순환해야 팀 하네스다. (멘토링 2026-08-19)
- session team 프리미티브는 토큰 소모가 과해 사용하지 않기로 팀에서 결정했다.

### 대안

- 개인별 `~/.claude` 하네스: 지식이 개인에 고립되어 기각.
- 런타임 팀 프리미티브 기반 설계: 이식성·토큰 문제로 기각.

### 영향

- 모든 하네스 산출물은 PR 리뷰 대상이 된다.
- 런타임별 차이는 symlink 계층(DR-002)에서 흡수하되, 흡수 범위는 스킬까지다
  (DR-002의 "범위 한계" 참조 — 에이전트 정의는 런타임별 소비 방식이 다르다).

## DR-002: 단일 소스는 `.agents/`, 런타임 디렉토리는 symlink

- 날짜: 2026-08-19
- 상태: 승인

### 결정

스킬과 에이전트 정의의 단일 소스는 런타임 중립 디렉토리 `.agents/`다.

```
.agents/
├── skills/   # 스킬 단일 소스
└── agents/   # 에이전트 역할 계약 단일 소스

.claude/skills → ../.agents/skills   (symlink)
.claude/agents → ../.agents/agents   (symlink)
.codex/skills  → ../.agents/skills   (symlink, 구버전 Codex 호환용 별칭 —
                                      현행 Codex는 .agents/skills를 직접 스캔)
```

### 근거

- SKILL.md는 오픈 표준이라 같은 파일이 Claude Code와 Codex CLI 양쪽에서 동작한다.
- Codex CLI(현행 0.149.0)는 프로젝트 레벨 `.agents/skills/`를 **네이티브
  스캔 경로**로 읽는다 — 단일 소스를 `.agents/`에 두는 선택이 Codex 쪽에서는
  symlink조차 필요 없는 정합이다. `.codex/skills` symlink는 구버전 호환용
  별칭으로만 유지한다.
- 복사본이 존재하면 반드시 어긋난다. 실제로 Claude→Codex 포팅 과정에서 스킬이
  변질된 사고가 있었다(멘토링 2026-08-19). symlink면 포팅 drift가 구조적으로 불가능하다.
- 이 레포는 이미 `AGENTS.md`(소스) ← `CLAUDE.md`(symlink) 방향을 쓰고 있다.
  중립 이름이 소스, 런타임 이름이 별칭이라는 같은 원칙을 디렉토리에도 적용한다.

### 대안

- `.claude/skills/`를 소스로, `.codex/skills`만 symlink: 특정 런타임에 소스가
  묶여 위 원칙과 어긋나 기각.
- 각 런타임 디렉토리에 복사: drift 사고 재발 경로라 기각.

### 영향

- 스킬·에이전트 파일 수정은 `.agents/` 아래에서만 한다.
- 런타임이 추가되면 symlink 한 줄로 대응한다.
- Windows 환경은 symlink 지원이 제한적이나 현재 팀은 전원 macOS라 문제없다.

### 검증

`.agents/skills/`에 임시 스킬을 놓고 발견 여부를 확인했다.

- 2026-08-19, Codex 0.148.0: 스킬 목록에 등장. 당시엔 `.codex/skills` symlink
  경유 발견으로 기록했으나, 아래 재검증으로 혼입 변수가 확인돼 정정한다.
- 2026-08-21, Codex 0.149.0 재검증 (Codex 교차 검토 지적 반영):
  - `.codex/skills` symlink를 **제거한 상태**에서도 발견됨 → Codex는
    `.agents/skills/`를 네이티브로 직접 스캔한다.
  - symlink 복원 후 같은 스킬이 1회만 노출됨 → 두 경로 공존에 의한
    중복 노출 없음.
- Claude Code: 세션 스킬 목록에 등장 — `.claude/skills` symlink 발견 확인.

### 범위 한계 (2026-08-21)

symlink가 흡수하는 런타임 차이는 **스킬까지다.** Codex의 네이티브 커스텀
에이전트는 `.codex/agents/*.toml`(별도 형식)이라 `.agents/agents/`의 역할
계약 md를 네이티브로 읽지 않는다. 역할 계약은 Claude Code에는 네이티브
에이전트 정의로, Codex에는 위임 프롬프트에 주입하는 역할 문서로 쓰인다.
toml 별도 정의 여부는 DR-013에서 "프롬프트 주입, 어댑터 미도입"으로 확정했다.

## DR-003: 스킬은 지식 문서를 복사하지 않고 경로로 참조한다

- 날짜: 2026-08-19
- 상태: 승인

### 결정

스킬은 `docs/conventions/`·`docs/knowledge/`의 내용을 본문에 복사하지 않는다.
"구현 전 `docs/conventions/layers.md`를 읽어라"처럼 경로만 가리킨다.

두 위치의 역할 구분:

| | `docs/conventions·knowledge` | 스킬 `references/` |
| --- | --- | --- |
| 담는 것 | 팀이 합의한 규칙·경험 (무엇이 올바른가) | 해당 절차 수행의 세부 (어떻게 작업하는가) |
| 독자 | 사람 + 모든 에이전트 | 그 스킬을 실행 중인 에이전트만 |
| 판정 기준 | 스킬을 지워도 팀에 유효하면 여기 | 스킬과 함께 없어져도 되면 여기 |

### 근거

- 같은 내용이 두 곳에 있으면 문서 갱신 시 스킬도 고쳐야 하고, 잊으면 어긋난다.
  실제로 이 문제 때문에 knowledge 폴더를 레포에서 뺐던 경험이 있다(멘토링 2026-08-19).
- 컨벤션 문서는 하네스 도입 과정에서 유실·변경되면 안 된다는 제약이 있다.
- 스킬 본문은 라우터로 얇게 유지하고 상세는 조건부 로드한다는 progressive disclosure
  원칙과도 일치한다. (하네스 책 ch5)
- 실험: 전문 주입 대신 "인덱스 + 검색 가능한 파일 구조"로 문서를 40KB→8KB로
  압축해도 통과율 100%가 유지됐다.
  (vercel.com/blog "AGENTS.md outperforms skills", 2026-01 — 프레임워크 문서
  지식 검색 도메인의 실험이라 모든 지식 유형에 일반화된 증거는 아니며,
  "경로 포인터로 충분"의 방향성 근거로 쓴다)

### 대안

- 컨벤션을 스킬 references/로 이관: 문서가 스킬 전용물이 되어 사람·타 에이전트의
  접근성이 나빠지고, "이동 중 유실 금지" 제약 위반 위험이 있어 기각.

### 영향

- 컨벤션 변경은 `docs/`에서만 일어나고 스킬은 수정이 불필요하다.
- 스킬 작성 시 인용이 필요하면 링크로 대체한다.

## DR-004: 라우팅은 AGENTS.md의 작업 유형 → 스킬 표로 한다

- 날짜: 2026-08-19 (개정 2026-08-21 — 오케스트레이터 경유 라우팅 폐기)
- 상태: 승인(잠정) — Step 6에서 이 레포 기준 트리거 검증(양성/음성/경계
  프롬프트) 후 확정. 등록도 그때 수행

### 결정

- 스킬의 자발적 트리거에 의존하지 않는다. 항상 로드되는 `AGENTS.md`에
  **작업 유형 → 워크플로우 스킬 4행 라우팅 표**와 하네스 포인터
  (목표·변경 이력)를 등록한다. 각 행에는 "어떤 요청이 이 유형인지"
  판별 기준을 한 줄씩 적는다.
- 라우팅 표의 행은 워크플로우 스킬 4개뿐이다. 공통 스킬·에이전트 등
  전체 목록은 적지 않는다(워크플로우 스킬이 명시 경로로 호출).
- 행 문구는 exact skill name과 **파일 경로를 병기**해 강제한다 — 예:
  "이 유형이면 다른 작업 전에 `.agents/skills/requirement-implementation/SKILL.md`
  전체를 읽고 따르라". 경로 병기 이유: Codex는 스킬이 많을 때 초기 목록에서
  일부를 생략할 수 있어, 이름만으로는 목록 누락 세션에서 불안정하다.
  겹치기 쉬운 유형(api-spec-definition vs api-connection)은 경계 기준과
  우선순위를 행에 명시한다. (Codex CLI 교차 검토 권고, 2026-08-21)

### 근거

- 실험: 스킬 자발 호출은 신뢰할 수 없다 — Vercel 실험에서 자발 미호출 56%,
  항상 로드되는 명시 인덱스는 통과율 100% vs 스킬 53%
  (vercel.com/blog "AGENTS.md outperforms skills", 2026-01).
  명시적 라우팅 지시가 있으면 호출률 95%+ (같은 실험; LangChain
  "Evaluating Skills"도 동일 방향).
- 위 실험이 지지하는 범위는 정확히 **"항상 로드 파일의 명시 라우팅 텍스트"**
  까지다. 라우팅 대상의 형태(워커 직접이냐 오케스트레이터 경유냐)에 대한
  증거가 아니다. 초기안(오케스트레이터 단일 등록)은 이 인용을 과대 적용한
  것이었고, 단일 진입점 형태를 지지하는 실험은 없어 폐기했다(DR-008 v2).
- 동작 원리: Claude Code는 CLAUDE.md를, Codex CLI는 AGENTS.md를 매 세션
  컨텍스트에 주입한다. 스킬은 name+description 메타데이터만 상시 노출되고
  본문 로드(호출) 판단은 모델의 확률적 선택이다. 따라서 반드시 물려야 하는
  라우팅 규칙은 항상-로드 파일 쪽에 두는 것이 구조적으로 강하다.
- drift 통제: 표는 4행이고 워크플로우 추가 시에만 변한다. 전체 목록 복사
  금지 원칙(하네스 책 ch10)은 유지된다.
- 수치 해석 주의: 56%·95%+·100%는 서로 다른 실험·지표·구성에서 나온 값이라
  방향 근거로만 쓴다. "4행 표" 형태 자체의 직접 증거는 아직 없으므로 이
  결정은 잠정이며, Step 6의 레포 기준 측정으로 확정한다. (Codex 교차 검토
  의견 반영)

### 추가 근거 (2026-08-21 웹 조사)

- 선택지 개수: 오선택이 정량 확인된 구간은 "유사 스킬 ~20개"(LangChain —
  20개에서 빈번한 오선택, 12개 통합 후 일관된 정선택,
  langchain.com/blog/evaluating-skills)와 "수백 개 도구·장문 컨텍스트"
  (LongFuncEval, arXiv:2505.10570 — 하락폭 7.6~85.6%, 단 프론티어 모델은
  완만)다. 워크플로우 4행은 모든 연구에서 고정확 구간이며, Meta 실험
  (arXiv:2605.24660)은 평균 7.4개 노출이 50개 노출과 동등(90.3% vs 90.8%,
  BFCL)임을 보였다 — 한 자릿수 후보 자체가 최적 구간.
- 자발 트리거 불안정의 교차 확인: LangChain에서 특정 스킬이 자발 호출 0회,
  명시 프롬프트로도 ~70%. 개인 650회 실측(Seleznov, 원문 미확인·참고치)은
  기준선 ~50%, CLAUDE.md 라우팅 추가 시 ~65%. Anthropic 공식 문서는 트리거
  신뢰도 수치를 제공하지 않고 "description 개선+모니터링"만 권고 — 벤더도
  자동 트리거를 보장하지 않는다.
- 경고(표 비대화): 단일 컨텍스트에 무관 도메인 지식이 2개 이상 로드되면
  성능이 급락한다(LangChain τ-bench 변형). 라우팅 표는 표만 얇게 유지하고
  스킬 본문은 호출 시 로드하는 현 구조를 지켜야 한다.

### 대안

- 스킬 description만으로 트리거: 위 수치로 기각.
- backend-orchestrator 단일 진입점 등록(초기안): 지지 실험 없음 + 간접 계층
  비용으로 폐기. 판별이 모호한 요청은 행별 판별 기준으로 커버하고,
  부족하면 Step 6 트리거 양성/음성 검증에서 데이터로 확인한다.
- 전체 스킬·에이전트 목록 등록: drift로 기각 (ch10).

### 영향

- 4개 워크플로우 스킬이 라우팅의 직접 대상이다. 공통 스킬(issue-context,
  ship-pr)은 워크플로우 스킬 본문이 명시 경로로 호출한다(DR-008 v2).
- AGENTS.md 갱신은 하네스 변경 이력 기록과 함께만 일어난다.

## DR-005: 실행 모델은 서브에이전트 단발 위임 + 파일 계약

- 날짜: 2026-08-19
- 상태: 승인

### 결정

멀티에이전트 실행은 "메인 세션이 서브에이전트를 단발 위임하고, 산출물은
worklog 파일 계약(DR-007)으로 주고받는" 모델로 한정한다.
런타임의 팀 프리미티브(session team, 에이전트 간 실시간 메시징)는 쓰지 않는다.

모든 생성-검증 루프에는 재시도 상한과 종료 조건을 명시한다:

- AI 리뷰 반영: 2회
- 테스트 실패 수정: 3회
- 리뷰봇 커멘트 대응: 2회
- 상한 도달 시: 실패 상태를 worklog에 명시하고 사람에게 에스컬레이트한다.
  조용히 계속 시도하거나 조용히 포기하지 않는다.
- 상한 수치(2·3회)는 실험적 최적값이 아니라 초기 운영값이다. 운영 데이터로
  조정한다.

### 근거

- 동작 원리: 두 런타임 모두 서브에이전트는 격리된 컨텍스트에서 실행되고
  에이전트 간 공유 메모리는 없다. 각 런타임은 이보다 풍부한 상호작용(조종·
  중단·스레드 전환 등)도 제공하지만, "단발 위임 + 반환"은 런타임의 한계가
  아니라 **양쪽에서 동일하게 동작하는 부분집합을 이식성을 위해 의도적으로
  선택**한 것이다. 턴 안의 반환 텍스트·조종 메시지는 지속되지 않으므로,
  턴·세션·런타임을 넘는 인계의 내구 채널은 저장소 파일뿐이다.
- 우리 워크플로우 4종은 모두 강한 순차 의존이고 에이전트 간 실시간 협상이
  필요 없다. 서브에이전트 판별 신호(산출물 독립·충돌 낮음·피드백 루프 없음)에
  부합한다. (하네스 책 ch9)
- 팀 모드가 주는 것 중 산출물 인계·상태·경계 계약은 파일로 대체 가능하다.
  대체가 성립하려면 파일 계약이 명시적이어야 한다 → DR-007. (같은 장)
- 재시도 상한 없는 검증 루프는 무한 루프 또는 조용한 품질 저하로 끝난다.
  상한+에스컬레이트는 필수 제한이다. (하네스 책 ch8)
- 3주 세션 데이터에서 상위 세션의 90.5%가 이미 위임 패턴을 쓰고 있었다
  (workflow_analysis, 2026-08). 효과 증거가 아니라 사용 관찰이다 — 이 모델이
  현 작업 방식과 마찰 없이 맞는다는 근거로만 쓴다.

### 대안

- session team: 토큰 소모·런타임 종속으로 기각 (DR-001).
- 위임 없이 단일 컨텍스트로 전부 수행: 긴 워크플로우에서 컨텍스트 오염과
  품질 하락(실행 drift)을 초래해 기각.

### 영향

- 각 워크플로우 스킬과 `.agents/execution-policy.md`는 "어느 단계를 메인이
  하고 어느 단계를 위임하는지"를 명시해야 한다.
- 순서 의존은 파일 존재 확인으로 표현한다(A의 산출물 파일이 있어야 B 시작).

## DR-006: 작업 산출물은 .worklog/에 커밋, _workspace/는 개인 스크래치

- 날짜: 2026-08-19
- 상태: 승인

### 결정

- 작업 산출물(계획·결정·TBD 기록)은 `.worklog/{이슈키}/`에 저장하고 커밋한다.
- `_workspace/`는 gitignore를 유지하고 개인 스크래치 전용으로 남긴다.
- worklog는 어떤 항상-로드 경로(AGENTS.md 등)에도 연결하지 않는다.
  해당 이슈를 작업할 때만 온디맨드로 읽는다.
- 정리 규칙: 이슈가 머지되고 일반화할 가치가 있는 내용은 `docs/knowledge/`로
  승격한 뒤, 오래된 .worklog 디렉토리는 삭제할 수 있다. 정교한 GC 정책은
  운영 경험이 쌓인 뒤 정한다.

### 근거

- 산출물은 작업을 명확히 하고, 인지 부채를 줄이고, 타인에게 컨텍스트를
  공유하기 위한 것이다. 커밋되지 않으면 마지막 목적이 죽는다.
  (팀 워크플로우 정리 문서, 2026-08)
- 단, 플랜·리포트 파일이 상시 로드 경로에 쌓이면 컨텍스트를 잠식한다.
  갱신 안 된 문서는 즉시 지우는 가비지 컬렉션이 가장 중요하다.
  (멘토링 2026-08-19) → "커밋하되 자동 로드에서 격리"로 두 요구를 모두 만족.
- 동작 원리·실험: 항상-로드 파일은 세션 시작 시 컨텍스트에 주입되어 이후
  모든 추론의 입력에 상주한다. 컨텍스트 파일 추가만으로 추론 토큰이 +10~22%
  늘었다는 측정이 있다(arXiv "Evaluating AGENTS.md", 2026-02). worklog까지
  상주 컨텍스트에 넣지 않아야 한다는 직접 근거다.

### 대안

- 산출물 gitignore 유지(현행): 팀 공유·승격 경로가 없어 기각.
- docs/ 하위에 저장: 큐레이션된 지식과 원시 작업 기록이 섞여 기각.

### 영향

- `.gitignore`의 `_workspace/`는 유지, `.worklog/`는 커밋 대상.
- worklog가 재실행 분기(이어하기)의 상태 저장소 역할을 겸한다(DR-007, DR-009).

## DR-007: worklog 파일 계약

- 날짜: 2026-08-19
- 상태: 승인

### 결정

`.worklog/{이슈키}/`의 파일명과 역할을 고정한다.

| 파일 | 역할 | 쓰는 시점 |
| --- | --- | --- |
| `plan.md` | 승인된 계획 + 체크포인트 체크박스 (진행 장부) | 계획 승인 시 생성, 체크포인트 통과마다 갱신 |
| `context.md` | 수집한 컨텍스트: 이슈 요약, PRD 링크·발췌, 관련 코드 위치 | 컨텍스트 수집 단계 |
| `decisions.md` | 구현 중 내린 결정과 이유 | 결정이 생길 때마다 |
| `tbd.md` | 미결정 사항, PRD·정책서에 반영해야 할 모호점 | 발견 시 |

- 파일이 필요 없으면 만들지 않는다(빈 파일 금지). `plan.md`만 필수다.
- 서브에이전트에 위임할 때 입출력은 이 파일들의 경로로 지정한다.
- `plan.md` 표기 규칙 (2026-08-21 추가, Codex 검토 반영):
  - 체크박스 `[x]`는 **사람이 승인한 단계에만** 표시한다. 실행만 끝난
    단계는 체크하지 않는다 — 체크 여부가 곧 재개 판별 기준이다.
  - 실패·에스컬레이트는 해당 단계 항목에 한 줄로 기록한다.
    예: `실패(재시도 2회 소진): 테스트 X가 계속 깨짐 — 사람 판단 필요`.
  - 상태 필드 체계(approved_at, retry_count 등)는 도입하지 않는다 —
    2인 팀에 과설계다. 운영에서 부족이 확인되면 그때 확장한다.

### 근거

- 팀 프리미티브 없이 서브에이전트+파일로 협업하려면 파일 계약이 곧
  통신 프로토콜이다. 경로·형식이 고정되지 않으면 대체가 성립하지 않는다.
  (하네스 책 ch4 입출력 프로토콜, ch6 경계면 계약)
- 파일명이 고정돼야 재실행 시 "무엇이 이미 됐는지"를 기계적으로 판별할 수 있다.
  (하네스 책 ch10 재실행 지원)

**plan.md 자체의 근거 (2026-08-21 추가):**

- 실측: 3주 세션 분석에서 `update_plan` 도구 호출 358회, 상위 세션 42개 중
  32개에서 관찰 — 계획 외부화는 이미 워크플로우의 고빈도 구성 요소다.
  Codex의 update_plan, Claude Code의 plan mode·태스크 추적 등 양 런타임이
  계획 외부화를 내장 프리미티브로 제공하는 것도 같은 사실의 방증. 단, 이
  내장 도구들의 상태는 세션 종료와 함께 소멸한다 — plan.md는 새 관행의
  도입이 아니라 이미 존재하는 관행의 내구화다.
- 동작 원리(DR-009의 성립 조건): 체크포인트는 턴 종료를 요구하고, 재개는
  새 세션·다른 팀원·다른 런타임일 수 있다. "어디까지 승인됐는가"는 재개
  주체가 반드시 알아야 하는 정보인데 세션 메모리는 세션과 함께 죽으므로
  (DR-005), 내구 채널인 파일이 없으면 체크포인트 프로토콜은 단일 세션
  안에서만 성립한다. 부수 효과: 긴 세션의 자동 압축으로 초기 계획이 요약
  손실돼도 파일에서 복원 가능.
- 방향성 실험: 성공률은 과제 길이에 급락하므로 과제 절단이 필요하고
  (METR, arXiv:2503.14499), 절단하면 절단면의 상태 기록이 필요하다. 실행
  오류가 컨텍스트에 누적되면 후속 성능이 추가 악화되므로(자기조건화,
  arXiv:2509.09677) 오염된 컨텍스트를 버리고 계획 파일에서 재시작하는
  구조에 가치가 있다.
- 한계: "plan.md 파일 유무" 자체의 A/B 실험은 없다. 표기 규칙(체크박스=
  승인)이 지켜지지 않으면 재개 판별 근거가 무너진다.

### 대안

- 자유 형식 산출물: 세션·사람마다 달라져 재실행 분기와 위임 입출력이
  성립하지 않아 기각.

### 영향

- 워크플로우 스킬들은 이 파일명을 하드코딩해서 읽고 쓴다.
- 계약 변경은 이 DR 갱신 + 스킬 일괄 수정으로만 한다.

## DR-008: 3분법 매핑 — 오케스트레이션은 각 워크플로우 스킬의 체크리스트가 담당

- 날짜: 2026-08-19 (개정 2026-08-21 — backend-orchestrator 폐기)
- 상태: 승인(잠정) — DR-004와 함께 Step 6 검증 후 확정

### 결정

| 책임 | 위치 | 담는 것 |
| --- | --- | --- |
| 오케스트레이션 (언제·누구와) | 각 워크플로우 스킬 본문의 번호 체크리스트 + 공유 실행 정책 문서 `.agents/execution-policy.md` | 체크리스트: 단계 순서·위임 경계·체크포인트 위치. 정책 문서: 체크포인트 규칙(DR-009), 재시도 상한·에스컬레이트(DR-005), worklog 계약 참조(DR-007), 재실행 분기 |
| 스킬 (어떻게) | `.agents/skills/` 6개: `requirement-implementation` · `api-spec-definition` · `api-connection` · `entity-design` · `issue-context` · `ship-pr` | 각자 자기 절차만. 본문 체크리스트(≤150줄) + `references/` 상세 |
| 에이전트 (누가) | `.agents/agents/` 역할 계약 (첫 번째: `code-reviewer`, 읽기 전용) | 역할, 판단 기준, 입출력 프로토콜, 에러 핸들링 |

- 독립 오케스트레이터 스킬은 두지 않는다. 라우팅은 AGENTS.md 표가
  직접 워크플로우 스킬로 한다(DR-004 v2).
- 워크플로우 스킬은 공통 단계에서 `issue-context`·`ship-pr`을 명시 경로로
  호출하고, 본문 서두에서 `.agents/execution-policy.md`를 따르도록 지시한다.
- 공통 단계 추출 근거: 4개 워크플로우 정의가 도입부(이슈·PRD 수집)와
  종결부(커밋·PR·리뷰봇 대응)를 공유함은 사전에 확인된 관찰 사실이다.
- `entity-design`은 절차가 짧아 스킬 가치가 불확실하다. 작성 후 With/Without
  비교로 유지 여부를 결정한다.
- `issue-context`·`ship-pr`을 스킬로 둘지 공유 절차 문서로 둘지의 판정
  기준은 **단독 호출 가치**다: 사용자가 독립적으로 부를 수 있으면 스킬
  (예: "커밋하고 PR 올려줘"), 워크플로우 내부 공통 단계에 그치면 공유
  reference 문서. 두 런타임 모두 스킬 간 네이티브 호출 프리미티브가 없어
  어느 쪽이든 "모델이 두 번째 파일을 읽는" 방식은 같으므로, 이 기준만으로
  Step 2·4에서 각각 확정한다. (Codex 교차 검토 의견)

### 근거

- 책 원문(ch3): 오케스트레이터는 "영속 파일에 고정되는 개념이라기보다 실제
  실행 흐름에 가깝다. 스킬 안의 번호 목록이 작은 오케스트레이터 역할을 했다.
  팀이 커지면 TeamCreate 같은 도구로 명시적으로 수행한다." — 우리는 팀
  프리미티브를 쓰지 않으므로(DR-005) 전자, 즉 스킬 내 체크리스트 형태가
  책이 제시하는 해당 규모의 정답이다.
- 책의 예제 오케스트레이터(ch11 코드리뷰 팀, ch12 풀스택 팀)는 **한 워크플로우
  안에서 다중 에이전트를 지휘하는 역할**이다. 서로 다른 워크플로우 여러 개를
  덮는 도메인 오케스트레이터를 만들라는 내용은 책에 없다.
- 도메인 단위 오케스트레이터가 효율을 올린다는 실험 증거는 없다. 인접 증거는
  반대 방향이다: 일반적 워크플로우 지시 구조물은 지시 준수는 만들지만 과제
  성공률을 올리지 못하고 비용만 늘렸다(arXiv "Evaluating AGENTS.md" 2026-02).
  오케스트레이터가 하려던 두 기능은 더 가벼운 수단으로 충족된다 —
  라우팅은 AGENTS.md 표(DR-004 v2, 실험 근거 있음), 공통 정책은 공유 문서
  (ch3의 "여러 요리사가 같은 레시피를 공유한다"와 동일 구조).
- 크기·복제 문제(v0.1의 대형 스킬 4개, v0.2의 가방 스킬 1개 기각 사유)는
  공통 스킬 추출 + 본문 라우터화(ch5 progressive disclosure)로 해소된다.

### 추가 근거 (2026-08-21 웹 조사)

우리 구조 그대로의 A/B(오케스트레이터 스킬 경유 vs 라우팅 표 직접 호출)는
공개 실험이 존재하지 않는다. 가장 가까운 정량 근거들은 방향이 일관된다:

- 중개 계층의 손실 (가장 근접): LangChain 멀티에이전트 벤치마크(τ-bench
  변형, GPT-4o)에서 중개 supervisor는 직접 핸드오프(swarm)보다 전 구간
  열세였고, 원인으로 지목된 "중계 번역" 손실을 보정하는 것만으로 성능이
  약 50% 회복됐다 — 중간 계층 자체가 그만큼의 손실원.
  (langchain.com/blog/benchmarking-multi-agent-architectures)
- 오케스트레이터-워커가 이기는 조건은 코딩과 반대: Anthropic 멀티에이전트
  리서치 시스템은 싱글 대비 +90.2%였지만, 이는 병렬화 가능한 리서치 태스크
  +토큰 15배 비용 조건이며 같은 글이 "대부분의 코딩 작업은 병렬화 가능한
  부분이 적어 부적합"이라고 명시한다.
  (anthropic.com/engineering/multi-agent-research-system)
- 실패 표면: MAST(arXiv:2503.13657, 1,600+ 트레이스)에서 멀티에이전트 실패의
  약 79%가 명세·시스템 설계(41.8%)와 에이전트 간 정렬(36.9%)에서 발생 —
  조율 계층을 줄이면 이 실패 표면 자체가 사라진다. (판본별 수치 차이 있음)
- 홉 비용: LLM 라우터의 분류 정확도 자체는 높다(Amazon arXiv:2412.05449,
  90%+, 오전환 <3%). 문제는 정확도가 아니라 홉당 지연 600~800ms·호출 비용·
  중계 손실이고, 다단계 판단은 p^n 복리 하락에 자기조건화 페널티가 더해진다
  (arXiv:2509.09677). 정적 라우팅 표는 이 홉을 0개로 만든다.
- 재검토 트리거: 위 근거들이 뒤집히는 조건은 "서로 유사한 스킬이 15~20개
  규모로 늘거나 이질적 도메인이 추가될 때"다(LangChain 오선택 임계 +
  distractor 도메인 2개 이상 급락). 그 시점에 계층화(라우터 도입)를
  재검토한다.

### 대안

- 워크플로우당 대형 스킬 4개 (v0.1): 500줄 한계(ch5) 초과 예정 + 공통부 4중
  복제로 기각.
- 단일 가방 스킬 `backend-workflows` (v0.2): 오케스트레이터와 스킬의 책임
  혼합, 내용물 목록형 이름 안티패턴으로 기각.
- 독립 `backend-orchestrator` 스킬 (v0.3): 지지하는 실험·책 근거 없음,
  간접 계층 추가 비용으로 기각.

### 영향

- 새 워크플로우 추가 = 워커 스킬 1개 추가 + AGENTS.md 라우팅 표 1행 추가.
- 스킬 이름은 능력을 그대로 서술한다. 내용물 목록형 이름("workflows" 등) 금지.
- 실행 정책 변경은 `.agents/execution-policy.md` 한 곳에서만 일어난다.

## DR-009: 체크포인트 실행 프로토콜

- 날짜: 2026-08-19
- 상태: 승인

### 결정

- 각 workflow 문서는 단계 중 사람 검토가 필요한 지점에 `[체크포인트]`를 표시한다.
- 워크플로우 실행(메인 세션)은 체크포인트에서 **턴을 끝내고** 산출물을 제시한
  뒤 승인을 기다린다. 승인 없이 다음 단계로 넘어가지 않는다.
- 기본값은 체크포인트 ON. 사용자가 "끝까지 진행해" 등으로 명시하면 해제한다.
- 진행 상태는 `.worklog/{이슈키}/plan.md`의 체크박스로 기록한다.

  이어간다.

### 근거

- 동작 원리: 두 런타임 모두 턴 중 개입 수단(권한 승인 프롬프트, 조종 메시지)이
  있지만, 이는 런타임·설정에 따라 다르고 산출물 검토를 위한 장치가 아니다.
  양쪽에서 동일하게 보장되는 검토 지점은 턴 경계뿐이므로, 이식 가능한 승인
  게이트는 "체크포인트에서 턴 종료"다.
- 텍스트 단계에서 고치는 것은 싸고, 구현 후 고치는 것은 비싸다. 계획이
  승인될 때까지 구현을 시작하지 않는 계획 우선 워크플로우가 실무에서
  검증돼 있다. (멘토링 2026-08-19)
- 한 턴에 많은 작업을 진행하지 않고 설계-검토 사이클로 진행하는 것이
  이 팀의 확립된 작업 방식이다.
- 단계별 정지를 스킬 분할로 구현하면 능력이 아닌 턴 경계 기준의 분할이 되어
  3분법 판별 기준(ch3)에 어긋난다. 정지는 실행 정책(execution-policy.md)의
  규칙이다.

### 대안

- 단계마다 스킬로 분할: 위 이유로 기각.
- 체크포인트 없이 전 과정 자동 진행: 구현 후 수정 비용 폭증으로 기각.
  단, 사용자 명시 해제는 허용(작고 명확한 작업).

### 영향

- plan.md(DR-007)가 체크포인트 장부를 겸한다.
- 워크플로우 소요 턴 수가 늘어나는 대신, 각 턴의 검토 범위가 작아진다.

## DR-011: 워크플로우의 추상화 수준 정의

- 날짜: 2026-08-21
- 상태: 승인

### 결정

하네스의 작업 단위는 3층으로 정의한다.

```
작업 요청 (이슈)     세션을 여는 단위. 기본은 워크플로우 1개, 드물게 연쇄(1:N)
  └─ 워크플로우      워커 스킬 1개의 단위 — 아래 3중 테스트를 모두 통과해야 함
       └─ 단계       체크포인트 사이 구간. 스킬로 만들지 않는다 (DR-009)
```

**워크플로우 = 독립적으로 검증·인도 가능한 산출물 하나를 만드는 절차.**
어떤 절차가 워커 스킬이 되려면 세 테스트를 모두 통과해야 한다:

| 테스트 | 질문 |
| --- | --- |
| ① 산출물 | 끝났을 때 독립적으로 리뷰·머지(인도) 가능한 산출물이 남는가? |
| ② 라우팅 | 사용자의 요청 문장만 보고 다른 워크플로우와 구분되는가? |
| ③ 지식 | 시작 전 읽어야 할 컨벤션·지식 세트가 다른 워크플로우와 다른가? |

- ①은 통과하나 ②·③이 실패하면 워크플로우가 아니라 기존 워크플로우의
  단계이거나 공통 서브루틴이다. (예: "테스트 작성"은 산출물이 있어 보여도
  요청 시점에 요구사항 구현과 구분되지 않으므로 ② 실패 — 독립 스킬이 아니라
  requirement-implementation의 단계)
- 합성 케이스(화면·요구사항이 모두 나와 스펙 정의→연결→구현을 한 번에
  처리)는 하나의 이슈에서 워크플로우를 **연쇄 실행**하는 것으로 다룬다 —
  각 워크플로우의 체크포인트는 유지되며, 정의 자체는 바뀌지 않는다.
- 현행 4개 적용: 요구사항 구현(Service+테스트 PR), API 스펙 정의(Controller+
  DTO+RestDocs(+모킹) PR — Service를 만들지 않음), API 연결(배선(+Facade) PR —
  스펙·Service가 이미 있음을 전제), 엔티티·테이블 설계(엔티티·schema.sql
  초안+정책서 뼈대). "Service를 만들지 않음 / 있음을 전제"가 스펙 정의와
  연결의 라우팅 경계 문장이다(DR-004의 행별 경계 기준).

### 근거

**① 산출물 테스트:**

- 실험: 에이전트 성공률은 과제 길이에 따라 시그모이드로 급락하며, 50% 성공
  시간 지평은 인간 기준 ~50분(2025년 발표, Claude 3.7 Sonnet 기준 — 지평은
  ~7개월마다 2배로 늘고 있어 절대값은 시점 의존적이나, "길이에 따른 급락"
  이라는 형태는 유지된다). 과제를 신뢰 가능한 길이로 절단하는 경계가
  필요하다는 정량 근거. (METR, arXiv:2503.14499)
- 실험(표준 조작화): 코딩 에이전트 평가의 사실상 표준(SWE-bench,
  arXiv:2310.06770)이 과제 단위를 "이슈 → 테스트로 검증되는 패치"로
  조작화했다. 분야가 이 입도에서 측정·최적화하므로 모델이 가장 신뢰 가능한
  입도도 이 층이다.
- 동작 원리(컨텍스트 수명): 세션 컨텍스트는 유한하고 차면 자동 압축(요약)돼
  세부가 손실된다. 산출물 경계가 있어야 그 지점에서 상태를 레포 파일로
  내리고 컨텍스트를 버릴 수 있다. 경계 없는 큰 워크플로우는 압축 생존을
  요구하는데 그런 메모리 모델은 런타임에 없다(DR-005와 동일 원리).
- 동작 원리(검증기 정렬): 이 레포의 결정론 검증기(테스트·ktlint·Flyway CI·
  리뷰봇)는 전부 커밋/PR 단위로 발화한다. 산출물 경계 = 확률적 실행이
  결정론 검증과 만나는 지점. 어긋나면 검증 없이 끝나는 실행 구간이 생긴다.

**② 라우팅 테스트:**

- 실험: 유사 후보 간 선택 정확도 급락 — hard query에서 16.7%
  (Meta, arXiv:2605.24660), 유사 스킬 ~20개에서 빈번한 오선택
  (LangChain "Evaluating Skills"). DR-004 추가 근거와 동일 출처.
- 동작 원리: 라우팅 표에서의 선택은 모델의 확률적 단일 판단이다. 행이
  요청 표현과 1:1로 매핑되지 않으면 오선택 확률이 구조적으로 열린다.

**③ 지식 테스트:**

- 실험: 무관 도메인 지식이 2개 이상 컨텍스트에 로드되면 성능 급락
  (LangChain τ-bench 변형). 장문·무관 컨텍스트의 성능 저하는 Lost in the
  Middle(arXiv:2307.03172) 계열에서도 반복 확인.
- 동작 원리: 스킬 호출 = 그 절차의 지식 세트를 컨텍스트에 로드하는 행위다.
  지식 세트가 같은 두 "워크플로우"는 분리해도 로드 내용이 같아 이득이 없고,
  지식 세트가 둘인 한 "워크플로우"는 매 실행마다 두 세트를 로드해 distractor
  페널티를 상시 부담한다. 지식 세트 경계가 곧 컨텍스트 최소화 경계다.

**이슈 층이 실제 호출 단위라는 실증:**

- 3주 세션 분석(상위 세션 42개): 초기 프롬프트에 MOI 이슈 키 42.9%,
  별도 worktree 40.5%, 이슈+Linear+Notion+PRD+worktree 풀 컨텍스트 묶음
  11건, 세션이 PR·외부 write로 종결되는 반복 signature. 멘토의 실무 흐름
  (이슈에 컨텍스트 → 플랜 → 구현 → PR)도 같은 층이다.

**단계를 스킬로 만들지 않는 근거:** DR-009(체크포인트) + 다단계 판단의
p^n 복리 하락·자기조건화(arXiv:2509.09677).

### 대안

- 워크플로우를 더 크게(예: "백엔드 개발" 하나): v0.2 가방 스킬로 이미 기각.
  ③ 위반 — 모든 지식 세트를 상시 로드.
- 워크플로우를 더 잘게(단계별 스킬): DR-009에서 기각. ② 위반 — 요청 시점
  구분 불가, 홉 증가.

### 영향

- 새 스킬 제안은 3중 테스트 통과 여부로 심사한다. 스킬 남설 방지 기준.
- 이슈:워크플로우 = 1:N 연쇄가 허용되므로, 각 워크플로우 스킬은 "선행
  워크플로우의 산출물이 이미 있는 경우"를 전제 조건으로 명시해야 한다.

- 날짜: 2026-08-23
- 상태: 승인 (사용자 지시 — "앞으로는 eval을 매우 가볍게만")

### 결정

DR-012의 측정 원칙(스킬의 TDD, 등록 전 베이스라인)은 유지하되, 실행
프로토콜을 경량화한다:

1. **풀 매트릭스 금지** — 전 스킬 × 전 프롬프트 × 다회 반복을 한 번에
   돌리지 않는다. 신규·변경된 스킬만 측정한다.
2. **기본 N=1, claude 단일 런타임** — codex는 스킬 발견 스모크(양성 1~2건)만.
   반복(N=2)은 결과가 판단을 가를 때만.
3. **차분 재측정** — description 수정 후에는 실패했던 프롬프트만 재측정한다
   (예: entity-design p4·p5 2건). 통과분은 재실행하지 않는다.
4. **풀 세트 재측정은 Step 6 최종 1회로 한정** — DR-004·008 확정용 전후
   비교. 그때도 claude N=1을 기본으로 한다.
5. 이미 확보한 측정치는 재실행 대신 score.py 재집계로 재활용한다
   (부분 측정도 폐기하지 않고 부분임을 명시하고 쓴다).

### 근거

- 실측: 2026-08-23 라운드가 102개 콜드 세션(3스킬 × 12프롬프트 × 3실행)을
  한 번에 소비 — 토큰 소모의 원인은 케이스 단건이 아니라 풀 매트릭스
  구조였다 (baseline-summary.md 비용 관찰).
- 지금까지 4개 스킬 측정에서 음성 오호출 0%가 일관 재현됐다 — 신호가
  안정적일 때 반복 횟수의 한계 정보 가치는 낮다.
- (정정 2026-08-23) 최초 근거로 들었던 "entity-design p4·p5 실패"는
  세션 사용량 한도 오염으로 판명(baseline-summary 교훈 8) — 재측정 결과
  실패가 아니었다. 대신 이 사건 자체가 경량화의 추가 근거다: 긴 배치는
  한도에 걸려 측정 자체를 무효화한다(entity-design claude 24건 중 19건).
- codex는 4스킬 연속으로 claude와 같거나 더 나은 트리거율을 보였다 —
  발견 스모크 이상의 전수 측정은 중복 정보다.

### 대안

- eval 전면 중단: 스킬의 TDD 원칙(DR-012)이 무너지고 description 회귀를
  못 잡는다 — 기각. 측정은 유지하되 표본을 줄이는 것이 맞다.

  또 필요하다 — 기각 (토스 루브릭 검토 때와 동일 결론).

### 영향

- Step 4~4b의 신규 스킬 eval은 "claude N=1 + codex 스모크"가 기본이 된다.
- entity-design 잔여 codex 6건(음성 4·경계 2)은 재실행하지 않는다.

## DR-019: entity-design 1단 논리 모델링(DBML)·2단 물리 모델링 명시

- 날짜: 2026-08-23
- 상태: 승인

### 결정

entity-design 1단은 개념 모델링과 논리 모델링을 한 번에 진행하고 산출물은
논리 모델 — `.worklog/{이슈키}/erd.dbml`(DBML)이다. 회의에서는 DBML

schema.sql로 반영한다.

### 근거

- erd-design 레퍼런스의 표준 절차(개념→논리→물리 모델링) 중 팀 미도입분
  채택 — 사용자 결정(2026-08-23). 단, 개념/논리를 단계로 쪼개지 않고 한
  번에 진행한다 — 2인 팀에서 산출물이 곧 논리 모델이면 중간 산출물의

- 논리/물리 분리는 회의 인풋의 관심사를 정책 판단(엔티티·관계·상태·제약)에

- 트리거 영향: description의 트리거 큐 문구("엔티티 모델링"·"테이블 설계"·

### 대안

- 전역 `docs/erd.dbml` 상시 유지: schema.sql과 이중 SSOT가 되어 드리프트
  필연 — 기각.
- 용어 사전 SSOT 동시 도입: 이번 범위에서 제외, tbd 예약 유지 —
  conventions 추가라 별도 승인 사안.

### 영향

- entity-design SKILL.md 1단·2단 개정. tbd 예약의 DBML·물리 모델링 항목

## DR-020: 정책 3층 재배치 — 결정론·상시·워크플로우 인라인 (DR-016 부분 개정)

## DR-022: qa-reviewer는 얇게 — 지식 분리와 플랫폼 경계

- 날짜: 2026-08-24
- 상태: 승인

### 결정

qa-reviewer(읽기 전용)를 레포에 두되 얇게 만든다: 판단 기준(변경 영향
분류·위험 신호·특수 검증 8문항)은 `docs/knowledge/qa-review.md`로 분리하고
에이전트 계약은 절차·입출력 배선만 담는다. 연결 위치는 ship-pr의 PR 전
QA 게이트 단일 지점. 경계: **레포 qa-reviewer = 머지 전 정적 diff 리뷰**,
**팀 개발 플랫폼 qa-engineer(배치 계획) = 배포 후 런타임 검증(sanity/smoke)**.

### 근거

- 두 QA는 대체재가 아니라 보완재다: 시점(머지 전/배포 후), 증거(diff+레포
  컨텍스트/실행 중 시스템), 잡는 결함 계층(접근 제어·호환성 설계 결함/
  통합·회귀)이 전부 다르다. BOLA류는 배포 후 smoke로 거의 안 잡힌다.
- 이식성: 지식을 에이전트 파일에 박으면 플랫폼 배치 시 이식 비용이 생긴다

### 결정

검사 로직은 `.agents/gates/`의 스크립트 한 벌(순수 로컬 파이썬, LLM 호출

## DR-028: 스킬의 가치는 산출물 품질이 아니라 모호점의 승인 전 표면화다

## DR-030: qa-reviewer 지적 반영 — 게이트 오탐과 eval 권한 경계

- 날짜: 2026-08-25
- 상태: 승인 (ship-pr 리뷰 게이트의 첫 실전 판정)

### 배경

하네스 PR을 우리 하네스(ship-pr)로 처리하면서 qa-reviewer에 위임한 결과
CONDITIONAL 판정과 필수 4건을 받았다. 도그푸딩에서 실제 결함이 나왔다.

### 결정

1. **시크릿 스캐너 오탐 제거** — `const val ACCESS_TOKEN = "ACCESS_TOKEN"`처럼
   값이 키 이름의 반복이거나 CONSTANT_CASE 식별자인 경우를 제외한다.
   실제 소스 2곳(인증 쿠키 상수, Testcontainers 자격증명)이 걸리고 있었다.
   구분 불가능한 테스트 자격증명은 `gate:allow-secret`으로 처리.
2. **훅의 시크릿 경고를 세션당 1회로** — `gate_hook.py`는 diff를 못 보고
   파일 전문을 스캔하므로 기존 줄까지 걸린다. 매 편집마다 BLOCK이 뜨면
   에이전트가 이를 해소하려 인증 쿠키 상수를 임의 변경할 수 있다.
   확정 차단은 diff 기반(pre-commit·CI)이 맡는다.
3. **eval 러너의 격리 워크트리 강제** — 트리거 프롬프트는 "구현해줘" 류
   실행 요청이고 claude 경로는 `bypassPermissions`로 돈다. 레포 루트 실행을
   거부하도록 `run.sh`를 수정했다. safety-policy의 "파괴적 작업 금지"와
   하네스 자체 도구가 어긋나면 계약 신뢰가 깨진다.
4. **CI 인터프리터 일치** — `pip install` → `python3 -m pip install`.
   불일치 시 PyYAML이 설치돼도 import에 실패하고 게이트 잡이 죽는다.
5. **게이트 셀프 테스트를 CI에 연결** + **실레포 오탐 0을 음성 테스트로
   추가**. 기존 음성 테스트가 합성 픽스처뿐이라 위 1번 결함이 새어나갔다.
6. **리뷰봇 ignore에 하네스 산출물 추가**(`.worklog/**`, `*.tsv`, `*.csv`,
   `.agents/evals/**`) — eval 기록·의사결정 장부가 리뷰 입력에 들어가
   비용과 노이즈를 만든다.
7. **`review-diff.patch`는 커밋하지 않는다** — DR-024에서 인계 계약을
   만들 때 커밋 여부를 정하지 않아 5,724줄이 커밋될 뻔했다.
   `.gitignore`와 worklog 계약에 명시.

### 근거

- 1·2번은 실측으로 확인했다(스캐너를 레포 전체에 실행). 특히 인증 쿠키
  상수를 에이전트가 건드리는 경로는 세션 쿠키 계약을 깨뜨린다.
- 5번이 핵심 교훈이다: **게이트의 음성 테스트를 합성 픽스처로만 하면
  실제 코드베이스의 오탐을 못 잡는다.** 실레포 전체 스캔을 회귀 테스트로
  넣어 같은 구멍을 구조적으로 막았다.

### 미반영 (후속 이슈)

qa-reviewer의 권고 중 다음은 팀 흐름을 막지 않아 이연한다: lint_skills의
SKILL.md 없는 디렉토리 처리, python3 부재 환경의 안내, pre-push의 remote
객체 부재 시 메시지 개선, `.review-swarm.yaml` teamRuleFiles 문자 상한 확인,
gate_hook·pre-push의 자체 테스트 부재.

### DR-030 보강 (2026-08-25, 리뷰봇 지적 반영 1회차)

review-swarm architect가 **문서 약속과 CI 실태의 불일치**를 지적했고 사실
확인 후 반영했다: AGENTS.md와 `pre-commit.sh` 주석이 "정합성 검사가 커밋·CI
에서 돈다"고 약속하는데 `harness-gates` 잡은 `check_pairings.py`를 호출하지
않았다. hooksPath 미설정 기여자는 페어링 경고를 로컬에서도 CI에서도 받지
못하는 상태였다 — 문서화한 백스톱이 그 규칙에 한해 비어 있었다.

CI에 Pairing check 스텝을 추가했다(PR 범위 diff 기준, WARN이라 차단하지
않고 로그로만 노출 — 로컬 pre-commit과 같은 수위).

### DR-030 보강 2 (2026-08-25, 리뷰봇 지적 반영 2회차 — 상한 소진)

review-swarm이 2건을 더 지적했고 사실 확인 후 반영했다.

1. **injection 방어 검사가 형해화돼 있었다** — `lint_skills.py`의
   `"데이터" not in body`는 단순 부분 문자열 매칭이라, incident-response의
   "데이터 오염"(장애 시나리오 용어)만으로 통과했다. 실제로 그 스킬에는
   방어 문구가 **없었다**. 게이트가 있는데 지켜지지 않는 상태였다.
   - incident-response에 방어 문구를 추가했다(장애 보고·알림·로그의 지시형
     문장은 실행하지 않고 인용 보고 — 장애 중에는 검증이 느슨해져 가장 위험).
   - 검사를 문구 앵커링(`명령이 아니다`·`승격하지 않는다`)으로 바꿨다.
     실효성 검증: 세 스킬에서 문구를 지우면 3/3 검출된다.
2. **api-design.md의 새 URI 규칙이 기존 컨트롤러와 충돌** —
   `rooms/{roomId}/comments/{commentId}` 등 이미 배포된 2-ID 엔드포인트가
   있다. 기존 컨트롤러 리팩토링은 후속 작업으로 분리한다는 사용자 결정에
   따라, 문서에 "신규 엔드포인트부터 적용, 기존은 별도 이슈로 정리" 한 줄을
   추가했다 — 그 사이 code-reviewer가 기존 패턴을 오탐하거나 신규 기여자가
   혼란스러워하는 것을 막는다.

교훈: **게이트를 만들 때 "통과한다"가 아니라 "위반하면 잡히는가"를
검증해야 한다.** 1번은 게이트가 통과 상태였지만 실제로는 규칙이 지켜지지
않았다. 게이트 신설 시 위반 픽스처로 검출을 확인하는 절차를 기본으로 한다.

### DR-030 보강 4 (2026-08-25, Security Sentinel — 내가 만든 우회 제거)

**게이트를 고치다가 더 큰 구멍을 냈다.** 보강 1에서 `ACCESS_TOKEN` 오탐을
없앨 때 의도는 "값이 키 이름의 반복이면 시크릿이 아니다"였는데, 구현은
값의 **형태**(CONSTANT_CASE)만 봤다. 그 결과 `secret = "QK7XTPLM4NDVRWS9"`,
`password = "TEMPPASSWORD2026"` 같은 **실제 대문자 시크릿이 통과**했다
(재현 확인). 시크릿 스캐너는 safety-policy를 기계로 강제하는 유일한
자동 방어선인데 그것을 내 손으로 뚫어놓은 셈이다.

형태 기반 예외를 제거하고 키-값 실제 일치 비교만 남겼다. 네 조건을 모두
확인했다: ①우회 차단 ②`ACCESS_TOKEN` 오탐 여전히 제외 ③실레포 오탐 0
④셀프 테스트 통과. 우회 케이스 3종(대문자 시크릿·키 이름 반복·인라인
주석)을 회귀 테스트로 못박았다.

교훈(보강 2의 확장): **오탐을 줄이는 수정은 미탐을 늘린다.** 오탐 수정
시에는 "정상 코드가 통과하는가"와 "진짜 위반이 여전히 잡히는가"를 함께
검증해야 하고, 완화 조건은 형태가 아니라 **의미**로 좁혀야 한다.

# MOI-549 하네스 수정 계획

## 목표와 범위

팀원이 PR만 읽고 “왜 했는가, 어떤 흐름으로 동작하는가, 무엇이 달라졌는가”를 이해할 수 있게 한다. 제품 요구사항·스펙 또는 필요한 ADR이 관련된 작업은 구현 전에 해당 Wiki 근거를 확인하고, 구현 후 코드·테스트·관련 명세를 대조한다. 하네스처럼 저장소 안에서 충분히 관리되는 작업은 Wiki를 조회하거나 문서를 만들지 않는다.

근거는 [context.md](context.md)와 [MOI-549](https://linear.app/100-thieves/issue/MOI-549)다. 사용자 논의로 수정한 내용을 포함해 전체 계획이 승인되었다. 사용자가 전체 계획 승인 후 구현 진행을 요청했다. 이후 Wiki는 제품 요구사항·스펙 또는 필요한 ADR에만 참조하도록 범위를 한정했다. 아래 구현·검증 산출물의 확인 항목은 계획 승인과 구분해 남긴다.

- [x] 전체 수정 계획 승인: 사용자 “나머지 계획은 다 승인할게”. 공통 진입·종료 지점으로의 통합, ship-pr의 마지막 게이트 역할, 필요한 명세 갱신의 후속 이연 금지, Claude Artifact 우선 및 대체 공유 문서 허용을 포함한다.

**필수 완료 조건: 현재 변경에 필요한 명세 갱신은 절대로 후속 TODO·후속 이슈·사람의 나중 작업으로 넘기지 않는다.** 구현 전에 필요한 갱신은 코드 작성 전에 끝낸다. 구현 중 또는 리뷰에서 추가 갱신 필요가 드러나면 같은 작업에서 원본 반영과 정합성 확인까지 끝낸다. 미결정 정책이나 접근 실패로 갱신할 수 없다면 해당 단계는 미완료로 남으며, PR 생성 또는 리뷰 대응 완료로 진행하지 않는다.

## 하네스 구조

기존 각 워크플로우의 **Pipeline + Producer-Reviewer** 구조를 유지한다. 주 에이전트가 순서와 파일 인계를 소유하고, 필요한 읽기 전용 리뷰어만 단발 위임한다. 별도 전역 오케스트레이터·Wiki 전담 에이전트·플랫폼 전용 SDK는 추가하지 않는다.

공통 기능은 독립 호출 가치가 있는 스킬 두 개로 분리한다.

| 역할 | 입력 | 책임·출력 |
| --- | --- | --- |
| `issue-context` | 이슈·사용자 요구·코드 | 읽기 전용 수집. 관련 Wiki 주소·요구사항 ID·모호점을 context.md/tbd.md에 기록 |
| `wiki-sync` 신설 | context·Wiki 원문·결정 근거·변경 코드/테스트 | 구현 전 모호점 해소·필요한 Wiki 갱신, 구현 후 정합성 대조. wiki-sync.md에 최소 증거 기록 |
| 기존 구현 스킬 | 구현 전 Wiki 확인 결과 | 기존 책임 범위에서 구현·테스트. 구현 중 새 모호점은 해당 변경을 진행하기 전에 Wiki 단계로 돌려보냄 |
| `change-brief` 신설 | context·decisions·최종 diff·검증 결과·Wiki | 배경·처리 흐름·전후 결과를 설명. change-brief.md와 공유 문서 링크(Claude Artifact 우선) |
| `qa-reviewer` 등 기존 리뷰어 | diff·관련 근거·Wiki 대조 결과·설명 자료 | 읽기 전용 교차 확인. 누락 또는 불일치를 근거와 함께 반환 |
| `ship-pr` | 검증된 변경과 위 산출물 | 파일 수·Wiki 확인·설명 링크를 확인하고 PR 작성. 리뷰 수정 후 필요한 확인을 다시 수행 |

기본 순서: 컨텍스트 수집 → Wiki 확인·모호점 해소 → 계획/스펙 → 구현 → Wiki 정합성 확인 → 설명 자료 → 리뷰·검증 → PR → 리뷰 수정 및 재검증.

## 1. 관련 제품 명세와 필요한 결정 근거에만 Wiki 확인 적용

- [ ] `AGENTS.md`에는 “제품 요구사항·스펙 및 필요한 ADR만 Wiki 참조”, “관련 명세는 구현 전 모호점 해소·구현 후 정합성 대조”, “필요한 명세 갱신의 후속 이연 금지”, “참조·수정한 Wiki가 있으면 PR에 링크”와 스킬 포인터만 둔다. 상세 절차를 상시 로드 파일에 복사하지 않는다.
- [ ] `issue-context`의 Notion 필수 검색을 제거한다. Notion 링크는 과거 참고 자료로만 취급하고, 제품 명세나 결정 근거가 필요한 경우에만 현재 Wiki 문서를 찾는다. 읽기 전용 수집과 정책 결정·수정 책임을 구분한다.
- [ ] `.agents/skills/wiki-sync/SKILL.md`를 신설한다. `pre`와 `post` 두 단계, 필요한 입력, 출력, 중단·재실행 조건을 명시한다. Wiki만 대조하거나 갱신하는 단독 요청에도 사용하되 하네스·로컬 문서만의 변경에는 호출하지 않는 경계를 정의한다.
- [ ] `pre`: 관련 Wiki 원문과 현재 코드를 읽고 모호점·충돌을 식별한다. 이미 합의된 내용을 명확히 하는 갱신은 수행하되, 제품 정책 선택은 추측하지 않는다. 결정이 필요한 항목은 질문하고 해당 구현을 진행하지 않는다. 필요한 Wiki 수정은 구현 전에 완료하고 재조회로 반영을 확인한다. 변경 필요가 없으면 확인 근거를 기록한다.
- [ ] `post`: Wiki의 요구사항/상태/권한과 코드·테스트를 항목별로 대조한다. 불일치는 **구현 결함 / 합의된 변경의 문서 누락 / 미결정 정책**으로 나눈다. 구현 결함을 덮으려고 Wiki를 바꾸거나, 오래된 문서만 믿고 코드를 임의 수정하지 않는다.
- [ ] PRD를 바꾸면 관련 `policy/_src/` 기록·인용·기준 날짜도 확인하고 Wiki 측 lint/정합성 확인까지 수행한다. 최신 `wiki_rules`와 실제 MCP 쓰기 계약을 확인하며, 생성 결과물 직접 편집 또는 로컬 PRD 사본으로의 우회를 금지한다.
- [ ] 공통 진입·종료 지점에 연결하고 개별 스킬에는 예외만 둔다. `issue-context`는 읽기 전용 근거 수집·모호점 식별을 담당하고, 주 에이전트는 `AGENTS.md`의 적용 조건에 해당할 때 구현 전에 `wiki-sync`를 수행한다. API 스펙/서비스 테스트 작성과 중간 단계 재개에도 이 원칙이 적용됨을 공통 규칙에 한 번만 명시한다. 6개 변경 스킬에 같은 지침을 복제하지 않는다. `entity-design`에는 팀 합의로 요구사항이 바뀐 경우 물리 구현 전에 Wiki를 다시 맞추는 시점만 명시한다.
- [ ] `ship-pr`은 단독 호출·작업 재개를 포함해 관련 Wiki 명세가 있는 변경에 대해 정합성 확인 결과와 필요한 명세 갱신의 완료 여부를 점검하는 마지막 게이트를 맡는다. 누락·불일치가 있으면 해당 작업으로 돌아가 해결하고, 이미 확인한 내용은 관련 변경이 있을 때만 다시 검토한다. 현행 “PRD 반영 사항을 PR에 적어 사람이 나중에 수정”하는 문구를 제거한다. 필요한 갱신이 남아 있으면 후속 TODO로 넘겨 PR을 생성하거나 리뷰 대응 완료를 선언할 수 없다.
- [ ] Wiki 비대상인 하네스·저장소 문서 변경은 로컬 근거로 진행하며 Wiki 결과 파일·링크를 요구하지 않는다. 제품 명세나 결정 근거가 필요한데 찾을 수 없거나 접근할 수 없는 경우만 해당 결정을 미완료로 남긴다. 문서 부재만을 이유로 관계없는 Wiki를 만들지 않는다. 장애 진단은 기존 읽기 전용 범위를 유지한다.

**수정 지점:** `AGENTS.md`, `.agents/execution-policy.md`, `.agents/README.md`, `issue-context`·`ship-pr`, 신규 `wiki-sync`, `entity-design`의 합의 변경 후 재확인 시점, `.worklog/README.md`, `requirement-implementation/references/worklog-forms.md`, `qa-reviewer.md`. 다른 변경 스킬은 공통 규칙과 충돌하는 문구가 있을 때만 수정한다.

**이번 작업의 문서 경계:** 하네스 규칙은 코드 저장소에서 관리한다. 이번 작업에는 제품 명세·ADR 참조가 필요하지 않다. 착수 시 Wiki에 잘못 추가했던 하네스 규칙은 원복 후 재조회로 확인했다.

## 2. 인지 부채를 줄이는 설명 자료 스킬

- [ ] `.agents/skills/change-brief/SKILL.md`를 신설한다. 필수 구성은 ① 작업 배경과 이유 ② 대표 비즈니스 시퀀스와 중요한 실패 분기 ③ 바뀌기 전/후의 동작과 영향 ④ 검증 결과와 제한 ⑤ 관련 근거(참조한 Wiki가 있을 때만 Wiki 링크)다.
- [ ] 시스템 경계·배포·외부 의존이 달라질 때만 아키텍처 그림을 추가한다. 문서·하네스 변경은 실제 작업 흐름을 설명하며 존재하지 않는 비즈니스 로직을 꾸며내지 않는다. 작은 변경의 설명은 짧게 유지한다.
- [ ] 설명 원문은 `.worklog/{작업키}/change-brief.md`에 둔다. 시퀀스는 코드로 확인한 흐름을 Mermaid 등으로 표현한다. PRD 전문이나 구현 목록을 복제하지 않고 팀원이 이해할 동작과 결정 이유를 적는다.
- [ ] 게시 절차는 `references/publishing.md`로 격리한다. 사용자 확인에 따라 **Claude Artifact 우선, 다른 공유 가능한 문서도 허용**한다. 플랫폼이 바뀌어도 설명 내용 계약은 유지한다.
- [ ] 연결된 도구로 Claude Artifact를 생성·공유할 수 있으면 사용하고, 지원되지 않으면 팀이 열람할 수 있는 GitHub의 저장소 Markdown 등으로 게시한다. 하네스 설명을 위해 별도 Wiki 페이지를 만들지 않는다. 모든 게시 수단이 없을 때만 내용을 먼저 완성하고 사용자에게 게시 및 링크 제공을 요청한다. 로컬 HTML 생성이나 URL 자리표시자를 실제 공유 완료로 처리하지 않는다. 팀 리뷰어의 링크 접근과 다이어그램 표시를 확인한다.
- [ ] `ship-pr`은 PR 본문에 설명 자료 링크를 넣고, 리뷰 중 동작이 바뀌면 자료도 갱신한다. Wiki 링크와 설명 자료 링크의 역할을 분리한다.

**수정 지점:** 신규 스킬·플랫폼 reference, `AGENTS.md` 라우팅, `.agents/README.md`, `.worklog/README.md`, `ship-pr`, `.github/PULL_REQUEST_TEMPLATE.md`.

## 3. PR 파일 수와 스택 검증

- [ ] `docs/conventions/git.md`에 **20개 이하 권장 / 21~50개는 분할 검토와 사유 명시 / 51개부터 차단**을 명시한다. 범위 분할은 계획 때 검토하고, PR 생성 직전과 리뷰 변경 후 실제 수를 다시 확인한다.
- [ ] `.agents/gates/check_pr_scope.py`를 추가한다. 실제 PR base와 head의 merge-base 기준 diff를 집계한다. 스택 PR은 바로 앞 브랜치가 base이며 항상 dev와 비교하지 않는다. 추가·수정·삭제·이름 변경을 포함하고 worklog·생성 파일도 제외하지 않는다. 이름 변경은 diff 항목 한 건으로 세며 NUL 구분 입력으로 경로의 공백 등을 처리한다.
- [ ] PR 전 로컬 점검은 커밋 전 변경과 미추적 산출물까지 확인하고, 깨끗한 최종 커밋 상태에서 다시 집계한다. CI는 이벤트의 실제 PR base/head를 사용한다. base를 못 찾으면 0개로 통과시키지 않는다. push 이벤트의 전체 추적 파일 수를 PR 변경 파일 수로 오인하지 않는다.
- [ ] `ship-pr`과 `.github/workflows/ci.yml`에 같은 검사기를 연결한다. 기존 `check_pairings.py`는 WARN 전용이므로 강제 상한을 그 안에 숨기지 않는다.
- [ ] `ci.yml`과 `review-swarm.yml`의 PR base 필터를 스택 브랜치에서도 실행되게 조정한다. `pull_request` 이벤트·fork 제한·최소 권한을 유지하고 `pull_request_target`으로 바꾸지 않는다. dev push 성공에만 진입하는 배포 경계도 보존한다.
- [ ] PR 템플릿에 해당할 때만 Wiki 수정/참조 링크와 정합성 확인 요약, 설명 자료 링크, 범위 및 앞/뒤 PR 관계를 추가한다. 자동 게이트는 파일 수를 검사하고, `ship-pr`은 필수 링크와 확인 결과를 검토하며, 실제 의미의 일치는 리뷰어가 판정한다. 필드가 존재하는 것을 정합성 통과로 간주하지 않는다.
- [ ] 스택의 상위 PR을 변경·머지하면 하위 PR base와 브랜치를 다시 정렬하고 검증한다. 완료되지 않은 하위 작업이 있는데 첫 PR의 `Closes MOI-549`로 이슈를 조기 종료하지 않도록 이슈 종료 링크는 전체 완료 PR에서 사용한다.

**수정 지점:** `git.md`, `ship-pr`, PR 템플릿, 신규 검사기와 테스트, 기존 gate test runner, `ci.yml`, `review-swarm.yml`. Actions 변경은 구현 시 `infra-change`의 보안·운영 경계와 검증 절차를 적용한다. 이번 변경은 Terraform 구성·자원을 바꾸지 않으므로 Terraform plan 비대상 사유를 명시하고 actionlint·이벤트/권한/배포 계약 검사로 검증한다. `infra-change`에도 변경 표면별 검증 분기를 명확히 하여 Actions만 바꾸는 작업이 불필요한 Terraform plan을 기다리지 않게 한다.

## 4. 리뷰 수정은 기존 커밋에 반영

- [ ] `git.md`의 “리뷰 반영은 fix(review) 등 별도 커밋” 규칙을 바꾼다. 최근 대상 커밋은 amend, 이전 대상 커밋은 fixup + autosquash 등으로 원래 관심사에 반영한다. 임시 fixup 커밋은 push 전에 정리한다.
- [ ] `ship-pr`의 현재 “계보가 갈라지면 무조건 중단” 분기를 보완한다. **확인한 기존 PR head에서 시작한 의도적 리라이트**와 원인 불명의 divergence를 구별한다. 원격 head·변경 범위·range-diff 등으로 확인되지 않는 리라이트는 진행하지 않는다.
- [ ] 원격 head를 사전에 확인하고 그 값을 대상으로 한 `--force-with-lease=refs/heads/<branch>:<확인한 원격 head>`를 사용한다. 보호 브랜치(main/dev)는 제외하며 일반 `--force`를 쓰지 않는다. lease 실패는 다른 변경이 생겼다는 신호로 보고 덮어쓰지 않는다.
- [ ] 리라이트된 최종 커밋별 빌드 가능성과 관련 검증을 확인한다. 변경된 동작에 대해서는 Wiki·설명 자료도 재검토하고, push 이후 최신 PR head의 체크 결과를 확인한다. 이전 head의 성공을 재사용하지 않는다.
- [ ] PR 생성 후 worklog를 갱신하지 않는 기존 규칙을 지킨다. 리뷰 근거·원격 head·range-diff·재검증 증거는 저장소 밖 임시 파일과 반환 메시지로 전달하고, 필요한 코드·테스트·관련 문서 수정만 작업 트리에 남긴다. 스택 하위 브랜치 리라이트도 같은 lease 확인을 적용한다.

## 파일 인계와 재실행 계약

- 저장소의 기존 `.worklog/` 계약을 사용한다. `docs/harness/`나 새 공용 `_workspace/` 구조는 추가하지 않는다.
- `wiki-sync.md`(Wiki 적용 대상일 때만): 실제 Wiki URI/팀 열람 링크, 필요한 요구사항 ID, 모호점과 결정 근거, 변경 여부와 이유, 구현 전 재조회 결과, 구현 후 코드/테스트 대응과 불일치 판정만 기록한다. 원문 전체·커밋 해시·PR/CI 상태를 복제하지 않는다.
- `change-brief.md`: PR 생성 전 사람용 설명 원문 스냅샷과 게시 링크. PR 생성 뒤에는 이 스냅샷을 수정하지 않고 공유 문서를 최신화하며, 수정 원문은 저장소 밖 임시 파일로 전달한다. 필요시 PR 생성 전의 `_workspace/{작업키}/`는 게시 준비용 임시 파일에만 사용한다.
- 기존 context.md·decisions.md·tbd.md를 재사용하고 내용 없는 파일은 만들지 않는다. `tbd.md`는 “Wiki 반영 대상 / 결정 근거 / 해결 여부”가 드러나도록 양식을 고친다. 필요한 명세 갱신을 적은 항목은 현재 작업에서 해결할 미완료 항목이며 후속 작업으로 이연하는 근거가 될 수 없다.
- PR 전에는 위 증거를 worklog에 남긴다. PR 후 재검토에서는 같은 의미의 증거를 저장소 밖 임시 파일로 생성해 리뷰어에게 전달한다. 기존 worklog의 통과 기록만으로 재검토를 생략하지 않는다.
- `qa-reviewer`는 입력 증거와 실제 diff를 함께 비교한다. Wiki 적용 대상인데 확인 증거가 없으면 “코드만 검토해 통과”로 완료 표시하지 않는다. Wiki 비대상 작업에는 로컬 요구사항·테스트 근거를 확인한다. 주 에이전트가 최신 Wiki를 조회해 읽기 전용 리뷰 입력으로 제공한다.
- Wiki 접근 실패·미결정 정책·설명 자료 게시 실패는 해당 의존 단계가 미완료임을 명시한다. 독립적인 점검·자료 준비는 계속할 수 있다. 접근 실패나 재시도 상한 도달도 필요한 명세 갱신의 이연 사유가 되지 않는다. 불확실한 내용을 추측해 채우거나 완료 판정을 내리지 않는다.
- 기존 리뷰 수정 2회·테스트 수정 3회·리뷰봇 대응 2회 상한을 적용하고, 범용 추가 재시도 계층은 만들지 않는다.

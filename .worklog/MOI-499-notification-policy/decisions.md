# MOI-499 결정 기록

## worker는 보내는 쪽이 완성한 공통 형식의 알림만 읽는다
- 갱신: 아래 "outbox 에는 … 도메인 사실(이벤트)을 저장한다" 결정 뒤로 공통 형식은 outbox 가 아니라 Redis 에만 있다. core-api 의 알림 소비자가 만든다.
- 날짜: 2026-09-24
- 내용과 이유: 기존에는 worker가 이벤트 종류마다 payload의 업무 필드를 해석하고 문구도 직접 만들었다. 이벤트를 추가할 때마다 worker를 고쳐야 했고, API가 worker보다 먼저 배포되면 새 이벤트를 해석하지 못해 알림이 실패 보관함(dead letter)으로 갔다. 사용자가 "worker가 비즈니스 필드에 강하게 영향받으면 안 된다"고 정했다. 그래서 API 쪽이 받는 사람·전송 정책·제목·본문·이동 경로를 담은 공통 형식을 만들어 outbox에 저장하고, worker는 이 형식만 읽는다. `eventType`은 worker에서 문자열로만 다룬다(로그·메트릭·푸시 data).
- 대안:
  - 템플릿 키와 값만 보내고 worker가 문구 생성: 새 이벤트마다 worker에 템플릿을 추가해야 해서 배포 순서 문제가 남는다.
  - 알림 테이블에 저장하고 메시지에는 ID만: 앱 내 알림함이 필요해지면 적합하다. 지금은 새 테이블·마이그레이션이 과하다. 공통 형식을 그대로 컬럼으로 옮길 수 있어 나중에 넘어가기 쉽다.
  - worker가 업무 테이블을 직접 조회: 결합이 가장 강해 제외.

## 여러 명에게 가는 알림은 발행 시점에 받는 사람마다 이벤트를 만든다
- 대체됨: 아래 "outbox 에는 … 도메인 사실(이벤트)을 저장한다" 결정으로 사실 1건이 outbox 1행이 되었다. 받는 사람별로 나뉘는 것은 Redis 메시지다. 한 사실의 메시지를 한 번에 넣어 이미 받은 사람에게 다시 가지 않는 효과는 유지된다.
- 날짜: 2026-09-24
- 내용과 이유: 사람마다 outbox 행과 Redis 메시지가 따로 생겨, 한 사람에게 보내다 실패해 재시도해도 이미 받은 사람에게 다시 가지 않는다.
- 대안: 이벤트 하나를 worker가 받는 사람별로 나누기 — 일부 실패 후 재시도하면 이미 받은 사람에게 중복 발송된다.

## 푸시는 한 기기라도 성공하면 전달된 것으로 보고 재시도하지 않는다
- 날짜: 2026-09-24
- 내용과 이유: 이슈의 기준("기기 중 하나라도 성공하면 전달")을 따른다. 일부 기기의 일시 오류로 재시도하면 이미 받은 기기에 중복 발송된다. 성공이 없고 일시 오류가 있을 때만 재시도한다. 성공이 없고 나머지가 만료 토큰·영구 오류뿐이면 "전달 안 됨"으로 끝내고, PUSH_ELSE_EMAIL이면 메일로 넘어간다.
- 대안: 기존처럼 영구 오류를 실패 보관함으로 보내기 — PUSH_ELSE_EMAIL에서 메일로 넘어가지 못한다.

## 8시간 자동 완료 경로에는 이번에 알림을 붙이지 않는다
- 날짜: 2026-09-24
- 내용과 이유: 자동 완료가 worker에 있는 것은 위치가 잘못됐다고 판단했고, 다른 팀원이 core-api로 옮긴다. 옮기면 같은 완료 이벤트를 발행하기만 하면 된다. worker에 outbox 행 직접 저장 코드를 새로 얹지 않는다.

## 리뷰 공개 알림의 중복 방지는 분산 락 대신 조건부 UPDATE로 한다
- 날짜: 2026-09-24
- 내용과 이유: `notified_at is null`인 행만 채우는 UPDATE가 1을 돌려준 쪽만 알림을 발행한다. 알림 발행(outbox 저장)과 같은 트랜잭션이라, 서버 여러 대가 같은 후기를 동시에 골라도 한 번만 나간다. 새 Redis 락과 설정을 만들 필요가 없다.
- 대안: `RedisOutboxRelayCoordinator` 같은 Redis 락 — 락 키·설정·테스트용 대체 구현이 늘어난다. 락이 만료되는 경계에서는 결국 조건부 UPDATE 같은 장치가 다시 필요하다.

## 리뷰 notified_at 백필은 기존 후기를 모두 알린 것으로 채운다
- 날짜: 2026-09-24
- 내용과 이유: 공개 전 후기만 남기려면 `visible_at`과 DB `NOW()`를 비교해야 하는데, 앱은 `Clock.systemDefaultZone()`으로 시각을 쓰고 DB 세션 시간대와 같다는 보장이 없다. 잘못 비교하면 과거 후기 알림이 배포 직후 한꺼번에 나간다. 배포 직전 3시간 안에 쓰인 후기의 알림을 포기하는 쪽을 택했다.

## 확정·취소 전 대기 신청자는 id만 조회한다
- 날짜: 2026-09-24
- 내용과 이유: `closeAllPending` 벌크 UPDATE는 호출 트랜잭션이 `RoomApplicationEntity`를 로드하지 않는다는 전제로 동작한다. 알림 받을 신청자를 엔티티로 읽으면 벌크 이후 영속성 컨텍스트에 낡은 행이 남는다. 그래서 신청자 id만 돌려주는 조회를 따로 두었다.

## outbox 에는 알림 요청이 아니라 도메인 사실(이벤트)을 저장한다
- 날짜: 2026-09-24
- 내용과 이유: 사용자 결정. 알림 말고 다른 소비자(통계·알림함 등)가 같은 사실을 쓸 수 있게 확장 여지를 둔다. 도메인 코드는 발행 창구 `OutboxEventPublisher.publish(EventType, payload)` 하나만 부르고, outbox 에는 `Event(eventId, type, payload)`가 들어간다. `EventType`마다 payload 클래스가 정해진다. 받는 사람 목록도 발행 순간의 사실로 payload 에 담는다(나중에 다시 조회하면 그 사이의 변화로 결과가 달라진다).
- 알림은 core-api 의 알림 소비자가 커밋 뒤 outbox 를 옮기는 시점에 사실을 받는 사람별 알림(공통 형식)으로 바꿔 Redis 에 넣는다. worker 는 이전과 같이 공통 형식만 읽는다 — "worker 는 업무 필드를 모른다"는 앞선 결정을 지키기 위해서다.
- 전송 정책은 이벤트가 아니라 알림에 붙는다. 확정 한 건이 참여자(PUSH_AND_EMAIL)와 닫힌 대기 신청자(PUSH_ELSE_EMAIL) 알림을 함께 만든다.
- 대안: worker 가 사실을 직접 해석 — worker 가 업무 필드에 묶이고 이벤트를 추가할 때마다 worker 배포가 필요해 제외.
- 영향: 사실 1건이 알림 메시지 여러 건이 된다. 여러 건은 한 Lua 스크립트로 넣어 일부만 들어가는 상태는 없다. 전부 넣은 뒤 outbox 완료 기록 전에 죽으면 다시 넣는 중복은 기존 at-least-once 경계와 같다.

## 읽지 못한 outbox 행은 지우지 않는다
- 날짜: 2026-09-24
- 내용과 이유: db-reviewer 지적. 배포 중에는 이전·새 버전 API 서버가 함께 돈다. 이전 버전이 새 이벤트 종류의 행을 집어 지우면 이벤트가 조용히 사라진다. 모르는 종류는 선점을 풀어 새 버전이 가져가게 하고, 형식이 깨진 행만 `UNREADABLE` 상태로 남긴다(지우지 않고 사람이 확인).
- 대안: 로그를 남기고 지우기 — 처음 구현이었으나 위 이유로 바꿨다.

## 탈퇴는 전용 도구(MemberWithdrawer)가 회원 행을 잠그고 처리한다
- 날짜: 2026-09-24
- 내용과 이유: 탈퇴가 회원 삭제와 대기 신청 철회를 한 커밋으로 묶는다. 참가 신청 제출이 회원 → 신청 순서로 잠그므로 탈퇴도 회원 행을 먼저 잠가야 같은 회원의 제출과 겹칠 때 서로를 기다리며 멈추지 않는다. 여러 개념을 조합하므로 `MemberManager`가 아니라 전용 도구에 둔다(layers.md).

## 읽을 수 있는 outbox 행의 소비 실패에는 시도 횟수 상한을 두지 않는다
- 날짜: 2026-09-24
- 내용과 이유: 사용자 결정. 소비자가 같은 이유로 계속 실패하는 경우는 없다고 가정한다. 소비 실패는 Redis 장애처럼 시간이 지나면 풀리는 실패로 보고 선점을 풀어 계속 재시도한다. 상한을 두면 긴 장애 동안 멀쩡한 사실까지 빠지는 문제도 생긴다. 형식이 깨진 행만 `UNREADABLE`로 뺀다.

## MOI-541(#137·#138) 머지 뒤 합친 방식
- 날짜: 2026-09-27
- 알림 규칙: 이미 머지된 #138의 받는 사람을 지우지 않고 이번 작업 규칙을 더했다. 확정은 방장 포함 참여자 + 닫힌 대기 신청자, 취소는 참여자 + 취소한(나간) 방장 + 닫힌 대기 신청자, 완료는 확정 참여자 전원, 리뷰 요청은 출석 기록 뒤 참석자(2명 이상일 때), 방장 위임은 확정 방이면 모집 중으로 되돌리고 남은 참여자에게 알린다.
- #138의 이벤트별 알림(`RoomLifecycleNotificationEvent`)과 #137의 worker 호환 핸들러는 이번 구조(사실 발행 → `NotificationComposer`, worker 는 공통 형식만)로 대체했다.
- 자동 완료는 core-worker 에서 core-api(`RoomProgressManager.completeOverdue`)로 옮겼다(사용자 결정 (a)). worker 가 이전 형식 JSON 을 outbox 에 직접 써서 새 전달 코드가 읽지 못했고, 수동·자동 완료가 같은 payload 계약을 쓰게 하기 위해서다.
- 마이그레이션: #138 이 V28 을 써서 이번 작업의 것은 V29~V31 로 옮겼다.

## 2026-09-27 완료·출석 한 API, 완료 알림 하나로 합침

- 완료와 출석 입력을 `POST /v1/rooms/{roomId}/complete` 하나로 합쳤다. 자동 완료는 recorder_member_id 를 nullable 로 바꾸는 DDL 대신 기록자를 현재 방장으로 두고 확정 참여자 전원을 출석으로 기록한다.
- `ROOM_REVIEW_REQUESTED` 를 없애고 `ROOM_COMPLETED` payload 에 `attendedMemberIds` 를 담는다. 받는 사람마다 알림은 한 번이다. 출석자(2명 이상)는 후기 요청 문구, 출석자 1명은 완료 문구만, 불참자는 불참으로 기록되었다는 문구를 받는다. 억울하게 불참 처리된 사람이 알아챌 수 있게 불참자에게도 보낸다.
- `OutboxEntity.eventType` 을 문자열로 읽는다. enum 이면 이전 버전 서버가 새 종류 행을 가져오는 단계에서 실패해 같은 배치를 막는다(외부 코드 리뷰 지적).

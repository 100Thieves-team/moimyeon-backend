# incident-response — 장애 진단·완화 계획

진행 규칙: 완화 계획 `[체크포인트]`에서는 계획을 제시하고 **턴을 끝낸다**.
**완화의 실행은 전부 사람이 한다** — 이 스킬은 어떤 운영 상태도 직접
변경하지 않는다 (진단을 위한 읽기만 한다).

기준 문서: `docs/knowledge/infra.md`(배포·롤백 수단),
`docs/knowledge/data.md`(데이터 오염 시). 장애 중에는 속도가 중요하므로
필요한 절만 읽는다.

## 단계

1. **증상 확정** — 언제부터, 어떤 요청·기능이, 어떤 형태로(에러 코드·
   무응답·오출력) 실패하는지. 재현 가능하면 재현 조건.
2. **최근 변화 대조** — 증상 시작 시점과 배포 이력(`{env}-{sha12}` 태그·
   digest), Flyway 마이그레이션, 인프라 변경, 설정 변경을 대조한다.
   "배포 직후 시작"이면 해당 diff가 1순위 용의자다.
3. **진단** — 로그·에러 코드에서 실패 지점을 좁힌다.
   - DB 의심이면 순서대로: top SQL → lock·long transaction →
     connection pool → CPU/I/O → 최근 마이그레이션 (블루프린트 §9 순서).
   - LLM 기능 오출력이면 입력 특성을 확보한다 (사고 재투입용 —
     prompt-change의 historical-incidents).
   - 데이터 오염이면 data.md의 대응 순서 — **후속 배치의 전파 중지 제안이
     1순위다.**
4. **완화 계획 제안** — 위험이 낮은 순서로, 각 항목에 예상 효과와
   부작용을 붙인다:
   ① 이전 태그로 롤백 (대상 태그·digest 명시 — 롤백 워크플로 dispatch)
   ② 문제 기능 제한·설정 변경 ③ batch 중지 ④ connection 제한·스케일
   ⑤ 데이터 직접 변조는 **최후이며 계획만** — 실행 여부·순서는 사람이
   결정하고 사람이 실행한다.
   **[체크포인트: 완화 계획]**
5. **완화 결과 수신** — 실행한 항목·대상 버전·결과·복구 확인 증거·잔여
   위험을 사람(또는 플랫폼)에게서 받아 타임라인에 기록한다. 복구가
   확인되기 전에는 사후 기록을 완료로 표시하지 않는다.
6. **사후 기록** — 원인과 교훈을 `docs/knowledge/`의 해당 파일에 한 줄
   추가하고, 재발 방지가 규칙감이면 conventions 반영을 제안한다.
   LLM 관련이면 해당 입력의 eval 셋 재투입을 prompt-change에 연결한다.
   worklog에 타임라인(증상→진단→완화→복구)을 남긴다.

## 하지 않는 것

- 운영 상태의 직접 변경 — 롤백 dispatch 클릭·설정 변경·쿼리 실행 전부
  사람 몫이다.
- 진단 없이 완화부터 제안 — 원인 가설 없는 롤백 제안은 하지 않는다
  (단, 배포 직후 전면 장애는 "직전 배포 롤백"이 정당한 1번 가설이다).
- 장애 중 코드 수정 — 영구 수정은 복구 후 원 워크플로우로.
